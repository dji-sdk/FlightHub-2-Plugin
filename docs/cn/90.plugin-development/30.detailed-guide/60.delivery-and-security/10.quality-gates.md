# 质量门禁

门禁是发布前必须通过的检查，包括工程校验、插件测试、交付包检查和目标环境联调。构建成功只证明产物可以生成，不能替代功能与安全验证。

## 单插件工程门禁

脚手架生成的工程自带以下核心命令，提交前至少跑一遍（`test` / `tsc` / `lint` 是否存在因模板而异，按工程 `package.json` 实际声明的脚本执行）：

```bash
pnpm run generate   # 生成类型
pnpm run validate   # 清单、流程、脚本一致性校验
pnpm run build      # 构建
```

`build` 不是简单打包。它会依次：校验清单 → 生成类型 → 检查代码与声明一致 → 构建入口和界面 → 校验产物 → 原子替换 `dist/`。首轮失败立即退出；持续监听模式下普通失败保留上一份成功产物。

## 插件测试与交付包检查

在插件自己的工程中执行已配置的类型检查、单元测试和端到端测试，不依赖平台源码仓库的维护脚本。至少覆盖：

- 参数校验、错误分类、状态推进、幂等和失败恢复。
- 扩展点显示、界面通信、宿主切换和卸载后的资源释放。
- 前后端接口字段一致，以及调用失败时界面可以恢复。
- 安装包结构、资源引用、版本与契约范围正确，未混入源码凭据或开发缓存。

CI 中需要浏览器测试时，应准备与测试框架匹配的浏览器；未执行的测试不能因为构建成功而视为通过。

## 目标环境验证

本地模拟器不能替代已部署环境。发布前由插件开发者和部署方共同确认业务表、连接配置及相关能力已经准备好，并用隔离测试数据验证流程接线、信号等待、重复消息和真实存储行为。设备相关操作还需确认测试项目与设备授权，不能用模拟结果代替真实设备状态。

## 必须人工确认的联合检查

自动化门禁查不出"前后端说好的事情没对齐"。发布前人工确认：

1. 前端调用的 `pluginId` 写的是**后端插件**的 ID。能力工程里前后端 ID 通常不同（如 `exp_demo` 与 `exp_demo_backend`），调用时以前端封装里的常量为准，不要手拼。
2. `ctx.apiCall()` 的路径、请求和返回结构与后端 HTTP 接口处理函数对齐。
3. 前端订阅的 WebSocket `bizCode` 与后端 `notify.publish` 发出的一致。
4. 写操作使用稳定的 `Idempotency-Key`；事件处理脚本按"至少一次投递"设计。
5. 前后端版本、契约范围、资产摘要进入同一份发布记录（见[能力版本发布](./40.capability-release.md)）。
6. 设备动作用真实机型验证过，包括超时后"结果未知"的场景。

## 新旧后端契约不要混用

当前创建向导生成的完整 Capability 和后端工程使用新契约：HTTP 接口处理函数按 `handlers/` 目录约定发现。历史工程中 `handlers[]` 显式登记的旧格式不再是推荐路径，其校验结果不能当作生产后端包的验收依据，生产后端包以新契约为准（见[行业包构建与打包](./20.industry-package.md)）。

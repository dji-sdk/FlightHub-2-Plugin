# 行业包构建与打包

平台上传的是行业包：包内按能力组织前端、后端插件。纯前端、纯后端或全栈能力都使用这一结构。`build` 生成各插件的构建资源，`pack` 将交付成员组装成一个 zip。

## 在工作区根打包

完成[质量门禁](./10.quality-gates.md)后，在创建向导生成的外层工作区根执行。该目录包含 `package.json` 和 `packages.json`：

```bash
pnpm run pack
```

模板脚本已选择内层能力工程，`pack` 会重新构建交付成员。使用本次 `UPLOAD_READY` 打印的实际 ZIP 路径，保留原文件名；不要凭目录名推算路径或上传上一次的产物。Yarn 和 npm 工程分别使用已有的 `yarn run pack`、`npm run pack` 脚本，保持创建工程时选定的包管理器。

聚合多个能力的行业工作区，在安装工具链的工作区根执行 `pnpm exec fh2-plugin pack`；直接选择单个能力时，用 `--root "<能力工程绝对路径>"`。执行目录、可选参数和兼容上下文见[工具链命令行参考](../70.api-reference/10.frontend/70.toolchain-cli.md#打包上下文)。

`pack` 生成未签名产物，不启动调试服务，也不上传或安装。终端的 `UPLOAD_READY <zipPath>` 表示产物已生成；上传后的解析与安装结果需在平台确认。

## 检查上传包

工具链生成的 zip 根直接包含 `packages.json` 和能力目录，不再套一层 `<packageId>/`：

```text
packages.json
<capabilityId>/
├── capabilities.json
├── frontend/<pluginId>/
│   ├── plugin.json
│   └── dist/...
└── backend/<pluginId>/
    ├── plugin.json
    ├── scripts/...
    ├── workflows/...
    └── schema.sql
```

上图展示同时含前后端的能力，按工程实际成员保留目录。后端脚本的实际路径以运行时 `plugin.json` 中的引用为准；`schema.sql` 只在使用数据实体时需要。

- `packages.json` 声明行业包及能力成员，能力 ID 与目录对应。
- `capabilities.json` 声明能力信息，插件放在该能力的 `frontend/` 或 `backend/` 下。
- 每个插件目录名与其清单 `pluginId` 一致，同一包内插件 ID 不重复。
- 平台识别的是能力 / 行业结构。独立 `<pluginId>/plugin.json` zip 不能直接上传；平台允许生态能力包省略 `packages.json` 的兼容方式，不改变工具链的标准输出结构。

## 前后端构建产物

工作区的 `pnpm run build` 构建成员，各插件分别输出自己的 `dist/`。它适合先检查构建错误；交付时仍执行工作区的 `pack`。

| 成员 | 插件内 `dist/` | 进入上传包后 |
| --- | --- | --- |
| 前端 | `fh2-plugin.json`、入口和各 View 的 JS/CSS、静态资源 | `frontend/<pluginId>/plugin.json` 加 `dist/` |
| 后端 | `plugin.json`、编译后的 HTTP / 事件 / 流程脚本、流程 JSON 和声明的资源 | 复制到 `backend/<pluginId>/`，运行时资源位于该插件目录下 |

前端产物清单的 `manifestVersion`、`engines`、`buildInfo` 由工具链生成，不要写入源清单。`engines.platform` 表示前端运行协议要求；后端清单的 `contractsRange` 表示后端宿主契约要求，两者分别检查。

前端包清单 `plugin.json` 保存 `pluginId`、`name`、`description`、`version` 和内嵌 `manifest`。内嵌清单不重复身份字段；其中的资源路径改为 `./dist/...`，`dist/fh2-plugin.json` 中的路径仍相对 `dist/`。这些转换由工具链完成。

后端 HTTP 脚本按 `handlers/` 目录约定发现，事件、流程与适配脚本由源清单引用。构建将 TypeScript 编译为普通 JS 并生成运行时清单，详见[后端清单](../20.development/20.backend/10.plugin-json.md)。流程包也可只包含流程及其声明的资源，不要求加入 TypeScript 脚本。

装载不会自动执行 `schema.sql`。发布前请部署方完成业务表准备与必要迁移；本地内存模拟器不能代替目标环境的数据库检查。

## 独立插件进入行业包

`frontend-basic`、`backend-basic` 生成的是独立源码工程。需要发布时，创建能力工作区，将完整源码工程迁入对应的 `frontend/<pluginId>/` 或 `backend/<pluginId>/`：保留源清单、`package.json`、构建与类型配置、源码、测试和引用资源，不复制 `node_modules`、缓存或旧 `dist/`。

确认成员纳入工作区后，重新安装依赖并执行类型生成、校验、测试和工作区 `pack`。保持 `packages.json`、`capabilities.json` 与成员身份一致，不用重命名独立 zip 或手工追加清单来拼上传包。

## 交付

默认 `pack` 生成未签名上传包。

记录本次 ZIP 的版本、摘要和成员，再按[安装、升级与回滚](./50.installation-and-upgrade.md#上传与安装)继续上传与安装。

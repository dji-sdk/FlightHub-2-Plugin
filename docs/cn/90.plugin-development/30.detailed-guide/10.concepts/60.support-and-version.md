# 支持范围与问题反馈

## 什么算"支持"

一个功能能不能在目标环境用，取决于三件事同时成立：

1. **SDK 里有**：SDK 目录中存在这个扩展点、能力或事件（见[能力总览](../30.features/00.index.md)）。
2. **目标宿主提供了**：插件要装的宿主注册了对应的能力实现。SDK 里有类型不代表宿主一定实现了。
3. **运行条件满足**：比如依赖当前页面状态、设备在线、用户权限。

所以代码里对 `ctx.capabilities.get()` 的返回值判空不是防御性编程，而是必须的可用性分支。

## 当前阶段的边界

- 前端插件的本地开发、调试、构建、预览链路已经可用。
- 后端插件的本地运行时可用；生产环境的安装、升级、流程编排随司空后端版本发布。
- 界面覆盖层的部分高级能力（如多流覆盖层组合）以各宿主实际注册情况为准。

拿不准某个能力在目标环境是否可用时，先在目标宿主里用最小代码试一下 `ctx.capabilities.get()`，再看[能力总览](../30.features/00.index.md)里对应宿主章节的说明。

## 反馈问题

提问题时请带上以下信息，能省一轮往返：

| 信息 | 示例 |
| --- | --- |
| 插件 ID 与版本 | `exp_project_demo 0.1.0` |
| 在哪个宿主、什么页面 | `project`，项目详情页侧边栏 |
| 复现步骤 | 1. 打开侧边栏 2. 点击按钮 3. 弹窗空白 |
| 第一条报错 | `validate` 或浏览器控制台的完整第一条错误 |
| 环境说明 | 本地调试页面还是真实司空；浏览器版本 |

**不要**在问题里附带：登录 token、插件 token、Cookie、未脱敏的业务数据或截图里的客户信息。

## 升级插件依赖

司空或 SDK 发布新版本后，升级插件的固定动作：

开发者工具交付不会因全局 CLI 重新 link 就自动更新工程依赖。先按[环境准备的源码与版本维护步骤](../20.development/40.hands-on/10.environment-preparation.md#保留源码与版本)构建固定的新版本源码，核对本地 `file:` 路径及相应覆盖，再在工程根安装、生成和校验。下方以 pnpm 为例；npm 或 Yarn Classic 工程保持原有包管理器。

```bash
pnpm install          # 更新依赖
pnpm run generate     # 重新生成类型
pnpm run validate     # 校验清单
pnpm run test && pnpm run tsc && pnpm run build
```

如果 `generate` 报类型变化，按新类型调整代码——不要把旧类型手工补回去。

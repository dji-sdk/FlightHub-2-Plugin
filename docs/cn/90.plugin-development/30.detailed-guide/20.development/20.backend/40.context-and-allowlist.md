# ctx 与能力注入

写后端脚本时，先记住一句话：`ctx` 只带这次调用的时间、幂等键和请求信息；数据库、网络、媒体这些能力不在 `ctx` 上，而是平台按 `allowlist` 注入的全局对象。

入口函数的签名是 `<入口函数>(input, ctx)`：HTTP 接口处理函数用动作名（如 `create`），事件回调和流程脚本用清单 `entry` 声明的名字。下面先看 `ctx`，再看能力对象。

- **`ctx`**：第二个参数，只装"这次调用的事实"（时间、幂等键），**没有任何能力**。
- **能力对象**：`store`、`cache`、`media`……不是从 `ctx` 取的，而是平台按 `allowlist` 直接注入的**全局对象**。

记住这条硬规则：**`ctx` 上没有能出网、能写库的方法；能力是全局对象，用没用由 `allowlist` 决定。**

> 前端插件的 `ctx`（`PluginContext`）是另一套模型。可选能力经 `ctx.capabilities.get()` 获取；受管 HTTP、事件、WebSocket 和存储直接使用对应 `ctx` 成员。后端能力按 `allowlist` 注入全局对象，不从后端 `ctx` 取，见[术语表](../../90.glossary.md)。

## ctx：这次调用的事实

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ctx.now` | string | RFC3339 时间。HTTP / 事件是每次处理时间；流程显式从步骤输入 `now` 接入 `run.now` 才有确定性时间，未接线为空 |
| `ctx.idempotencyKey` | string | HTTP 取 `Idempotency-Key` / 业务键，事件取 `event_id`，流程取步骤输入 `idempotencyKey`；缺失为空 |
| `ctx.requestId` | string | HTTP 请求追踪 ID；事件 / 流程为空，不是业务去重键 |
| `ctx.pluginVersion` | string | 当前包版本 |
| `ctx.stableId(scope)` | 函数 | 派生稳定业务 ID：幂等键 + scope 的哈希前 32 位。**没带幂等键就调用会直接报契约错**，平台不会生成随机值兜底 |

保留所选工具链生成的 `types/`，不手改产物。类型声明说明字段形状，字段何时有值及重试边界查[脚本上下文参考](../../70.api-reference/20.backend/40.context-api.md)。下面 HTTP 片段的 `ctx.now` 是本次调用时间，代码注释中的“重试不变”不适用于 HTTP 重发或事件重新处理；流程必须另外接入 `run.now`。

```ts
export function create (input: RecordInput, ctx: HandlerCtx) {
  const sessionKey = ctx.stableId('task-create')   // 幂等唯一键
  const nowMs = Date.parse(ctx.now)                // 平台时间（重试不变）
  // ...
}
```

## 能力：allowlist 注入的全局对象

在源清单 `fh2-plugin.json` 的 `allowlist` 里申报权限，平台就把对应的全局对象注入沙箱。**没申报的对象根本不存在**——不是调用报"未授权"，而是 `xxx is not defined`。

```json
{ "allowlist": ["data:read", "data:write", "media:read"] }
```

```ts
// 申报了就直接用，不需要任何获取动作
const page = store.query('task', { status: { eq: 'new' } })
if (!page.ok) {
  throw { code: page.error.code, message: '查询任务失败: ' + page.error.message }
}
const m = media.get(fileId)
log.info('done', { count: page.data.total })   // log 不需要申报，三路都有
```

| 常见误判 | 真相 |
| --- | --- |
| 少申报一个能力，调用时报"权限拒绝" | 未注入的方法或对象会在调用处失败，具体异常取决于访问方式；先核对有效 allowlist，不按异常名称猜权限 |
| 申报了能力名就能执行对应业务 | 注入只提供该能力的方法；部署的能力提供方是否可用、调用返回什么仍需另行确认 |

## 能力总表

| 全局对象 | 方法 | 需要的权限 | 哪些路线可用 |
| --- | --- | --- | --- |
| `log` | `info / warn / error` | 不需要 | 全部 |
| `platform` | `getConfig()` 读连接配置、`insertEvent(ev)` 写事件、`resolveSegment(lat,lng)` 解析路段 | `config:get`、`event:write`、`geo.segment:read` | 全部 |
| `connector` | `invoke(id, payload)` 调平台连接器、`fetch(req)` 受管出网 | `integration:write` / `integration.gis:read`、`egress:fetch` | 全部 |
| `store` | `query / count / insert / createIfAbsent / update / delete` | `data:read`（前两个）、`data:write`（后四个） | 全部 |
| `cache` | `get / set / del / expire / incr / setnx / …` | `cache:read` / `cache:write` | 全部 |
| `media` | `get / list`（读）、`attach / ensureFolder / move / rename`（写） | `media:read` / `media:write` | 全部 |
| `flow` | `start(flowName, bizId, seed)` 启动本插件的 job 流程 | `flow:start` | 三路按 allowlist |
| `notify` | `publish(...)` 给前端发通知 | `notify:publish` | 三路按 allowlist |
| `wayline` | `generate(...)` 示教航线生成 | `wayline:generate` | 三路按 allowlist |
| `screenshot` | `signUrl(key)` 预签名、`issueUpload(...)` 签发上传凭据 | `screenshot:signurl` / `screenshot:issueupload` | 三路按 allowlist |
| `objectTrack` | `inspect / getTrack` 读目标轨迹 | `track:read` | 三路按 allowlist |
| `video` | `probe / extractFrames / createClip` | `video:process` | 三路按 allowlist |

- HTTP、事件和流程脚本三路共用按有效 `allowlist` 注入的方法。
- `evaluators` 是第四种脚本入口，但注入面恒空，只能使用 `log`，不在这张三路能力表里。
- 流程脚本的非空 `scripts[].allowlist` 覆盖包级列表；为空或未写时回落到包级。
- 重耗时的视频处理建议放在流程作业里；这是超时与重试建议，不是按路线禁止注入。

**注入不代表部署的能力提供方可用**。申报后方法仍可能在调用点报未装配或返回 `skipped`，具体按各方法签名处理。流程脚本可以获得 `flow.start`，不应把路线当作递归防线；调用须评审稳定业务键、`seed` 和重试副作用。

Media 的方法可用性并不相同。`list` 当前不可用，`attach` 是空壳；`get`、`ensureFolder`、`move`、`rename` 在媒体能力已配置时可接真。写侧还依赖部署配置和 workspace 参数，逐方法边界见[媒体与通知](../../30.features/60.backend-capabilities/60.media-notification.md)。

`platform.getConfig()` 还要求已绑定的连接上下文：

- 流程步骤用 `inputs.connectorId` 选择已声明且由部署方赋值的连接。
- HTTP / 事件没有步骤级选择；`config:get` 已注入，不代表配置可读。

详见[连接外部系统](./80.external-connections.md)。

示教航线生成有两层限制：

- 不能仅依据可选字段猜默认值，也不能把候选声明当作当前 SDK 的等价替代。
- 调用前核对目标版本的机型 / 负载字段、正速度和至少两个有效航点。

未完成兼容验证时保留该调用的验证缺口，不把本地构建成功写成航线生成成功。

## 能力调用的返回形态

**不能把所有能力当成统一信封或统一抛错通道。** `store` 方法返回 `{ok:true,data}` 或 `{ok:false,error:{code,message}}`，失败需检查 `ok`。下面的 `must` 只适用于这种信封结果：

```ts
function must<T> (result: { ok: true, data: T } | { ok: false, error: { code: string, message: string } }, action: string): T {
  if (!result.ok) {
    // 把能力错误翻成你自己的业务错误抛出去（code 决定平台处置，见 HTTP 接口一页）
    throw { code: result.error.code, message: action + ' 失败: ' + result.error.message }
  }
  return result.data
}

const page = must(store.query('task', {}), '查询任务')
```

别直接 `String(result.error)`——error 是对象，拼出来是 `[object Object]`，唯一有用的线索就丢了。带上 `error.code`（如 `UNKNOWN_FIELD`），现场一眼能看出是列名写错还是库连不上。

`cache` 的返回与错误通道逐方法查工程生成的 `types/`。

其他能力按[能力目录](../../70.api-reference/20.backend/80.host-capability-catalog.md#返回与错误)中的具体签名处理。例如 `flow.start` 返回 `{already}`，不是 `{ok,data}`。不要对所有能力套用上面的 `must`。

- HTTP 接口处理函数、事件入口和流程脚本**必须返回对象**；无业务输出通常返回 `{}`。
- 事件入口顶层返回 `{ok:false,error:{code,message}}` 时，会按 `error.code` 分类消息处置。
- HTTP 接口处理函数和流程脚本**不自动提升返回的失败信封**；需要失败时应显式 `throw result.error`，否则可能表现为 HTTP 外层成功或步骤成功。

## 飞行控制不在能力清单里

下发任务、返航、抢控这类**高危动作不提供给脚本**——脚本拿不到任何飞行函数。飞行操作只能通过流程编排里的平台步骤（如 `dispatch_mission`）完成，平台在这些步骤上做权限和风控校验。详见[流程编排](./60.workflow.md)。

## 权限申报的纪律

- 按需申报：只用到的才写。申报了授不出的能力名，进程起不来。
- 流程 `scripts[]` 的非空 `allowlist` 覆盖包级；为空或未写时回落包级，不是合并。空列表不是撤销包级权限的方式。
- 加删能力要考虑包内所有脚本——包级 allowlist 是共享的，同包"只读接口"和"写接口"没有权限隔离。需要真隔离就拆成两个插件包。

# 流程编排

流程是后端插件的**异步编排**能力：把多个步骤按依赖关系组织成一张有向图，由平台负责调度、重试、超时和等待人工操作。一个流程 = 一个 JSON 文件，放在 `workflows/` 目录并在清单 `flows[]` 里登记。

## 什么时候用流程

| 诉求 | 用什么 |
| --- | --- |
| 单次、即时、要马上拿结果 | [HTTP 接口](./20.http-handler.md) |
| 事件到了做一次快速处理 | [消息订阅](./30.event-handler.md) |
| 多步骤、要重试、要等待（人工确认、飞行完成）、要定时 | **流程** |

## 一个最小的流程

流程 JSON 是插件资产。`build` 只生成构建产物，`pack` 构建并组装交付包，都不会启动网关或流程服务。工程含后端且未使用 `--frontend-only` 时，`dev` 启动的是本地 HTTP 模拟器，不是真实网关，也不执行流程。下面的启动、查询和信号接口需在已安装插件的测试环境验证；环境接入、授权和队列就绪由部署方确认。

`workflows/normalize.json`：

```json
{
  "name": "normalize",
  "description": "文本规范化示例",
  "trigger": { "api": { "seed": ["value"] } },
  "steps": [
    {
      "id": "run-normalize",
      "action": "run_script",
      "inputs": {
        "script": { "const": "normalize" },
        "value": { "from": "trigger.value" },
        "idempotencyKey": { "from": "run.idempotencyKey" }
      },
      "timeoutSec": 10,
      "maxAttempts": 1
    }
  ]
}
```

三要素：

1. **`name`**：流程的运行期身份。启动端点、定时调度、事件路由都用它。
2. **`trigger`**：怎么被触发（必须有，见[触发方式](./70.triggers.md)）。
3. **`steps`**：步骤列表，按 `needs` 声明的依赖关系执行。

启动一个 API 触发的流程：

以下 HTTP 片段表示已部署环境采用 Bearer 鉴权时的协议形状。前端使用 `ctx.apiCall` 由宿主处理凭据和前缀；其他调用方先取得测试环境的授权凭据，并按部署方提供的地址与前缀发送。入口要求其他认证头时按部署方说明替换，不可作为无鉴权请求直接照抄。

```http
POST /flows/normalize/start
Content-Type: application/json
Authorization: Bearer <ENV_API_TOKEN>

{ "bizId": "order-001", "trigger": { "value": "  DJI  " } }
```

> 谁来调这个端点：
> - **前端插件**：走 `ctx.apiCall('/flows/normalize/start', { method: 'POST', body: {...} })`，网关会自动加 `/plugin-api` 前缀并带上 token。
> - **其他服务 / curl**：使用部署方提供的测试环境入口与授权凭据，路径前缀以环境配置为准；本地 `dev` 不提供真实流程执行。
> - **插件自己的脚本**：不走这个端点，用 `flow.start()`（需要流程声明 `job` 轴，见[触发方式](./70.triggers.md)）。

返回的是**启动确认**（含 `workflowId`），不是执行结果；重复 `bizId` 会命中同一条流程实例（`already: true`）。执行进度用状态端点查询：

```http
GET /flows/normalize/incidents/order-001/status
Authorization: Bearer <ENV_API_TOKEN>
```

## 步骤（steps）

| 字段 | 说明 |
| --- | --- |
| `id` | 步骤身份，其他步骤用 `steps.<id>.<输出>` 引用它的结果 |
| `action` | 做什么：平台步骤（如 `dispatch_mission`）、`plugin.<名>`（插件自定义能力）、`run_script`（跑你的脚本） |
| `needs` | 依赖哪些步骤（数据依赖和顺序依赖都写在这里） |
| `trigger` | `allSucceeded`（默认：上游全部成功才跑）或 `allDone`（上游有终态就跑，常用于收尾） |
| `inputs` | 每个入参写 `{"const": ...}`（常量）或 `{"from": ...}`（引用） |
| `when` | 条件，不满足则跳过本步骤 |
| `delaySec` | 执行前延迟（秒），适合"等 30 秒再复检" |
| `await` | 等待信号（人在环），声明了本步骤就不执行动作、只等输入 |
| `timeoutSec` | 步骤超时（秒），上限 3600 |
| `maxAttempts` | 最大尝试次数，含首次执行；按动作区分单次尝试与可调整策略，见[重试边界](../../70.api-reference/20.backend/60.workflow-dsl.md#重试边界) |

### 数据从哪来：`from` 的三个根

```text
trigger.<路径>            触发时传入的数据
steps.<步骤id>.<路径>     前序步骤的输出
run.now                   平台时间（重试期间不变）
run.idempotencyKey        本步骤的幂等键
run.intervalSec           定时触发的间隔秒数（仅 schedule 触发的流程有）
```

注意：**数据来源必须在 `needs` 依赖链上**。想用某个步骤的输出，就要把它加进依赖链，没有"按名字全局取值"的机制。DAG 编辑期预检与本地 `validate` / `build` 不等于同版本权威后端校验；交付前仍须由部署方提供目标后端校验并验证运行，见[DAG 编辑](../../40.debug-and-test/14.workflow-editor.md)。

### 条件与分支

```json
{
  "id": "close-on-timeout",
  "action": "update_event_status",
  "needs": ["ack"],
  "trigger": "allDone",
  "when": {
    "and": [
      { "field": "trigger.eventId", "op": "present" },
      { "field": "steps.ack.$state", "op": "eq", "value": "timedOut" }
    ]
  },
  "inputs": { "status": { "const": "ack_timeout" } }
}
```

- 条件算子：`eq ne in exists blank present`，可用 `and` / `or` 组合。
- 每个步骤有终态：`succeeded / failed / skipped / timedOut / interrupted`，用 `steps.<id>.$state` 读取。
- 默认 `allSucceeded` 下，上游被 `when` 跳过（`skipped`）会传染给下游；想让"无论上游成败都收尾"的步骤执行，用 `trigger: "allDone"`。

## 平台步骤（受控动作）

这些动作由平台实现并把关，流程里直接写动作名即可：

| 动作 | 用途 |
| --- | --- |
| `dispatch_mission` | 下发飞行任务（唯一的飞行入口，带权限与风控校验） |
| `query_flight_task` | 查询飞行任务状态 |
| `spawn_agent` | 拉起巡逻会话以抢占设备控制 |
| `return_home` | 返航 |
| `update_event_status` | 更新统一事件模型的事件状态 |
| `wait_signal` | 等待信号（配合 `await`） |
| `run_script` | 执行清单 `scripts[]` 里的 JS 脚本（业务逻辑写在这里） |

**脚本能做的事和平台步骤是互补的**：脚本不获得飞行控制函数，下发任务用 `dispatch_mission`，返航等使用相应受控动作；业务计算放脚本。声明动作不代表目标设备、权限及下游能力已就绪。

每个平台步骤的入参出参契约见[平台步骤参考](../../70.api-reference/20.backend/60.workflow-dsl.md)。

## 人在环：等待外部确认

用 `await` 声明一个等待信号的步骤：

```json
{
  "id": "approve",
  "action": "wait_signal",
  "await": {
    "signal": "approved",
    "timeoutSec": 3600,
    "provides": [ { "key": "operator_id", "type": "string" } ],
    "optional": [ { "key": "remark", "type": "string" } ],
    "interruptedBy": [ "cancel" ]
  }
}
```

外部（前端、其他服务）把信号投递给运行中的流程：

```http
POST /flows/approval-flow/incidents/order-001/signals/approved
Content-Type: application/json
Authorization: Bearer <ENV_API_TOKEN>

{ "payload": { "operator_id": "user-001" } }
```

- 平台同步校验：信号名是否在声明内、当前是否在等它、必填键齐不齐、类型对不对、有没有多余键。校验不通过当场拒绝，不会污染流程历史。
- `timeoutSec` 到点后步骤终态是 `timedOut`，下游可用 `when` 感知并走超时分支。
- `interruptedBy` 声明的中断信号（如 `cancel`）会把步骤打成 `interrupted`。
- 信号投递成功只表示"已受理"，下一步是否执行完要查状态。

## 重试、幂等与确定性

流程跑在持久化工作流引擎上（负责调度、重试和断点恢复，你不需要直接操作它）：进程重启、机器故障后流程从断点继续。你需要配合的：

- **每步的幂等键**：`run.idempotencyKey` = 流程实例 + 步骤 ID，重试时不变。把它显式接进脚本入参，脚本内用 `ctx.stableId()` 派生业务 ID，重试才不会产生重复数据。
- **明确时间接线**：步骤 `inputs.now` 接入 `run.now` 后，脚本从 `ctx.now` 取得确定性时间。`now` 是平台种子键，不要写进 `scripts[].io.inputs`。HTTP / 事件的 `ctx.now` 是每次处理时间，不适用同一重放保证，见[脚本上下文](../../70.api-reference/20.backend/40.context-api.md)。
- **按动作核对重试策略**：默认最大尝试次数包含首次执行；`run_script` 与其他可重试动作的退避不同，非幂等受控动作不重试。准确值、显式调整和导出差异统一见[重试边界](../../70.api-reference/20.backend/60.workflow-dsl.md#重试边界)，不要据旧导出推断固定等待窗口。
- **整段脚本是重试边界**：失败后可能从脚本入口重新执行，已完成的外部调用不会回滚，也没有逐次能力调用的恢复点。调大尝试次数之前先审查整步副作用和去重。
- **错误分类影响重试**：契约错和业务结果（`NOT_FOUND` 等）会让步骤直接失败不重试；系统错误走重试策略。
- **不要把敏感信息放进流程**：流程输入、步骤输出、错误信息都会进入不可删除的执行历史。token、密码、签名 URL 一律不进。

## 一个完整的业务流程长什么样

事故快处置流程（业务骨架，不可直接交付）：省略了完整脚本 I/O 和动作必填输入。例如 `dispatch_mission` 还需要 `dockSn`、`projectUuid`，必须按[动作参考](../../70.api-reference/20.backend/60.workflow-dsl.md#平台受控步-受控动作)补齐接线并通过目标后端校验。

```json
{
  "name": "accident-response",
  "trigger": { "stream": { "match": { "status": "unacknowledged" }, "seed": ["eventId", "lat", "lng"] } },
  "steps": [
    { "id": "ack", "action": "wait_signal",
      "await": { "signal": "acknowledge", "timeoutSec": 3600 } },
    { "id": "pick", "action": "run_script", "needs": ["ack"],
      "inputs": { "script": { "const": "pick-dock" }, "lat": { "from": "trigger.lat" } } },
    { "id": "dispatch", "action": "dispatch_mission", "needs": ["pick"],
      "inputs": { "waylineUuid": { "from": "steps.pick.waylineUuid" } } },
    { "id": "close-timeout", "action": "update_event_status", "needs": ["ack"], "trigger": "allDone",
      "when": { "field": "steps.ack.$state", "op": "eq", "value": "timedOut" },
      "inputs": { "status": { "const": "ack_timeout" } } }
  ]
}
```

读法：事件到达 → 等人签收（1 小时）→ 签收后跑脚本选机场 → 下发飞行任务；若超时，另有一路把事件状态置为超时。

## 常见坑

| 现象 | 原因 |
| --- | --- |
| 流程启动返回 40301 | `trigger` 里没声明 `api` 轴，API 启动被拒 |
| `from` 引用报错 | 引用的步骤不在 `needs` 里，或路径拼错 |
| 脚本步骤拿不到 `store` 等能力 | 清单里该 `scripts[]` 项（或包级）没申报对应权限 |
| 重试后出现重复数据 | 脚本没用幂等键，或用了 `new Date()` 做后缀 |
| 信号投递返回 40901 | 流程当前不在等这个信号（查状态端点看 `awaitingSignal`） |
| 信号投递 504 | 后端运行时未及时处理；先查流程状态，再重发同一信号，仍失败时带流程 ID 联系技术支持或部署方 |

# 消息订阅与事件处理函数

平台会产生一些消息（比如"一张照片入库了""一段视频处理完了"）。后端插件可以在源清单里声明"我对某类消息感兴趣"，消息到达时平台自动执行你指定的函数。这不是 HTTP 调用，是平台主动找你。

## 什么时候用

- 媒体文件入库后做关联、归档、通知。
- 下游系统回调后触发后续动作。
- 任何"事件到了才需要做"的逻辑。

如果需要等待、重试、多步骤编排，用[流程编排](./60.workflow.md)；消息回调适合**单次、快速**的处理。

## 怎么声明

在源清单 `fh2-plugin.json` 的 `events[]` 里（脚本是 `.ts` 源文件，导出名写在 `entry`）：

```json
{
  "events": [
    {
      "description": "视频处理完成，触发后处理作业",
      "type": "media.video_created",
      "match": { "sub_file_type": "0" },
      "consumer": [
        { "handler": "events/on-video-created.ts", "entry": "onVideoCreated" }
      ]
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `type` | 消息类型。**平台指定**，当前有 `media.photo_created`（照片入库）、`media.video_created`（视频处理完成）。插件只能选，不能自造 |
| `match` | 筛选：消息体顶层字段必须等值匹配（多个条件是 AND）。不写 `match` 表示该类型全收 |
| `consumer` | 后端运行时中命中的消费方并发执行、各自独立重试；全部结束后按最坏结果聚合消息处置 |
| `consumer.handler` | 脚本路径（约定放 `events/` 目录），TypeScript 源文件 |
| `consumer.entry` | 导出函数名，缺省 `handle`。它指向你 TypeScript 里 `export` 的函数，和 HTTP 接口处理函数的目录命名是两套规则 |

一个类型可以配多个消费方（比如同一段视频回调，变道抓拍和行人上路各处理各的）；多个插件也可以订阅同一个类型，消息会发给每一个。

`consumer` 数组不保证执行先后。有业务依赖的逻辑应放在同一个消费函数内调用，或用显式流程编排，不能依赖另一个消费方先写完数据。

模板自带的 `example.created` 是**本地模拟联调专用**的消息类型：`pnpm run dev` 时用 `POST /plugin-api/mock/backend/event` 手工投递（工程 `backend/<id>/README.md` 有完整演示），不是真实平台消息。

本地模拟器不用于证明后端运行时的并发、独立重试或消息确认/死信处置；这些边界需在已部署的测试环境验证，投递与重放方式由部署方提供。

## 怎么写消费函数

> fh2-plugin-sdk 为文档使用的 SDK 模块名；实际路径使用生成工程配置。保留生成工程中的实际 import，不按文档模块名修改依赖或工具链别名。

```ts
// events/example-created.ts（模板自带）
import { ingestEvent } from '../shared/records'
import type { RecordInput } from '../shared/records'
import type { EventCtx } from 'fh2-plugin-sdk/backend'

export function onExampleCreated (event: RecordInput, ctx: EventCtx) {
  // 入参是消息信封 { id, type, data }，业务字段住在 data 里
  const nowMs = Date.parse(ctx.now)   // ctx.now 是本次处理时间（RFC3339），每次重试重新取值
  return ingestEvent(event, Number.isFinite(nowMs) ? nowMs : 0)
}
```

这段是模板的 `example.created` 本地输入示例，业务字段位于 `data`；不能将它当成真实媒体消息的统一形状。真实媒体消费函数按目标消息定义取字段，本地模拟器的包装差异见[后端调试](../../40.debug-and-test/30.backend-debugging.md#已知限制)。不要为适配本地模拟器给生产消费函数增加双形状兜底。

要点：

- 事件侧 `ctx.now` 是每次处理尝试的时间，不保证重试期间不变；需要稳定业务时间时使用消息中已校验的业务时间字段。`ctx.idempotencyKey` 取消息 `event_id`，不是投递标识；`ctx.requestId` 为空，见[脚本上下文参考](../../70.api-reference/20.backend/40.context-api.md)。本地 `example.created` 的 `{ id, type, data }` 包装不能代替真实消息协议。
- **入口必须返回对象**，通常为 `{}`；若入口直接返回辅助函数的结果，该结果也必须是对象。执行到函数末尾未返回、`return undefined` 或裸 `return` 会被后端运行时当作可重试错误，耗尽后丢弃（`Discard`）。
- 普通业务输出不会交给其他消费方，但事件入口顶层返回 `{ok:false,error:{code,message}}` 时，后端运行时会按 `error.code` 分类处置；把失败藏在嵌套对象里，或忽略失败后返回 `{}`，不会自动变成错误。
- **HTTP 接口处理函数和流程脚本不自动提升返回的失败信封**。若 `store` 操作失败应让调用失败，必须显式 `throw result.error`；不能将事件入口的信封分类规则套用到另两路。
- **"这条消息不是给我的"绝不抛**：同一条队列上可能还有别的消费方，你的契约错会把消息打进死信，拖累别人的投递——安静返回空对象就是正确处置。
- **"把媒体挂到业务记录上"的推荐做法**：在自己的实体里存 `file_id`（用 `store.update` 带条件写入）。`media.attach` 当前仍是空壳（返回 `skipped`），不要把它当成关联成功的依据；`ensureFolder` / `move` / `rename` 接真但依赖部署配置和 workspace 参数，见[媒体与通知](../../30.features/60.backend-capabilities/60.media-notification.md)。

## 投递语义：至少一次，所以必须幂等

同一条消息**可能到达多次**（重投、进程重启）。你的函数必须做到"执行两次和执行一次效果一样"：

| 场景 | 幂等手段 |
| --- | --- |
| 写关联记录 | `store.createIfAbsent` + 唯一键；或 `update` 带原状态条件，看 `affected` 行数 |
| 启动后处理流程 | `flow.start` 的 `bizId` 用业务 ID（同 ID 永远是同一条流程实例，重复调返回 `already`） |
| 发前端通知 | 只在"真的新建了数据"时发（`affected > 0` 才发），避免重复推送 |

```ts
// 例：只在真的绑上视频时才发通知
const affected = store.update('capture_event',
  { id: { eq: eventId }, post_status: { eq: 'pending_video' } },   // 条件里带原状态
  { video_file_id: fileId, post_status: 'waiting_artifacts' })

if (affected.ok && affected.data.affected > 0) {
  notify.publish({ channel: 'device', to: dockSn, bizCode: 'capture.event', subCode: 'video.bound', data: { eventId } })
}
// 本片段只通知本次新增的绑定；affected === 0 时不重复通知。
```

这是消费函数内的通知片段，入口最后仍须返回对象。若更新后还要启动流程，`affected === 0` 不能证明流程已启动；需检查同一绑定并补启，见[事件、通知与状态](../30.fullstack/30.events-and-state.md)。

## 错误与消息处置

| 脚本结果或错误 | 单个消费方的处置 | 适用 |
| --- | --- | --- |
| 正常返回对象（如 `{}`） | 确认（`Ack`） | 已处理或正常过滤 |
| `NOT_FOUND`、`DUPLICATE`、`CONFLICT` | 确认消息（`Ack`），不重投 | 业务上"这条消息不用处理"，比如没匹配到任何记录 |
| `INVALID_ARGUMENT` 等契约错 | 丢弃（`Discard`），不重投；已配置死信保存时进入死信队列 | 消息本身有问题，重投一万次也一样 |
| 其他错误或非对象返回 | 按部署的 `MaxAttempts` 有界重试，耗尽后丢弃（`Discard`） | 系统抖动或入口返回不符合约定 |
| 可重试错误处理/退避期间因关停取消 | 重新入队（`Requeue`） | 让下一次投递接手 |

错误分类同时适用于抛出的错误和事件入口顶层的失败信封。多个消费方全部结束后，对同一条消息按 **Requeue > Discard > Ack**（重新入队 > 丢弃 > 确认）取最坏结果；一个消费方失败不会阻止其他消费方执行，但最终处置仍影响整条消息。`MaxAttempts` 和队列的死信保存由部署方配置；丢弃（`Discard`）只有在队列配置了死信交换机时才进入死信队列，插件清单不负责这些配置。

```ts
// 没命中是常态：这个机场最近没有违章，而每段视频都会发回调。
// 明确抛业务档，让平台确认消息，而不是留着重试。
if (page.list.length === 0) {
  throw { code: 'NOT_FOUND', message: '窗口内没有待处理的事件' }
}
```

## 筛选（match）的注意事项

- `match` 对**消息体顶层字段**做字符串等值比较：`"match": {"sub_file_type": "0"}` 只收 `sub_file_type` 等于字符串 `"0"` 的消息。
- 更细的过滤（范围、组合条件）在消费函数里自己做。
- 消息字段名以平台消息定义为准，写错字段名等于没筛。

## 能力面

HTTP、事件和流程脚本三路共用按有效 `allowlist` 注入的方法，包括 `objectTrack`、`video`、`flow`、`notify` 等。重耗时的视频处理建议放在流程作业里，这是超时与重试设计建议，不是按路线禁止注入。对象存在不代表部署的能力提供方可用，仍须按具体方法签名处理结果或错误，见[ctx 与能力注入](./40.context-and-allowlist.md)。飞行/裸设备函数不注入脚本。

# HTTP 接口处理函数

后端插件对外提供接口的方式：把 TypeScript 脚本放进 `handlers/` 目录，工具链自动登记。调用方通过统一入口 `POST /plugin/invoke` 按名字调用。**没有独立 URL、没有路由配置**——一个入口、一个名字、一个函数。

## 接口怎么命名

**文件路径 + 命名导出 = 接口名**。一个文件一个接口，导出名用文件末段的动作名：

```text
handlers/example/create.ts    + export function create    → 接口名 example.create
handlers/example/list.ts      + export function list      → 接口名 example.list
handlers/task/archive.ts      + export function archive   → 接口名 task.archive
```

构建时每个 HTTP 接口处理函数会得到稳定入口名（`h_example_create`），调用方用 `example.create` / `example_create` / `h_example_create` 三种写法都能寻址。

新增一个接口 = 新增一个文件，**不用在清单里登记**。接口名就是你的 API 契约的一部分：改文件路径等于改接口名，调用方会跟着 404。

## 函数签名

> fh2-plugin-sdk 为文档使用的 SDK 模块名；实际路径使用生成工程配置。保留生成工程中的实际 import，不按文档模块名修改依赖或工具链别名。

```ts
// handlers/example/create.ts
import { createRecord } from '../../shared/records'
import type { RecordResult, RecordInput } from '../../shared/records'
import type { HandlerCtx } from 'fh2-plugin-sdk/backend'

export function create (input: RecordInput, _ctx: HandlerCtx): RecordResult {
  return createRecord(input, 'handler')
}
```

- 签名是 `<动作名>(input, ctx)`。`ctx` 只带请求信息（`now`、`requestId`、`idempotencyKey`、`stableId()` 等）；**能力不在 ctx 上**——`store`、`log` 这些是按清单 `allowlist` 注入的全局对象，没申报的对象根本不存在。
- `input` 是调用方传来的对象，**原样透传**：平台不做校验、裁剪或类型转换，参数校验自己写（`requireText` 那种）。
- 返回值必须是**对象**，原样放进响应的 `data`。返回字符串、数组或什么都不返回会当成系统错误。
- 不要把敏感信息（token、密钥、未授权的业务数据）放进返回值——没有输出裁剪，写了什么调用方就看到什么。

## 调用方式

所有调用方（前端、其他服务、curl）都走同一个入口。下面是已部署环境采用 Bearer 鉴权时的协议形状，不是无鉴权的本地请求：先向部署方确认测试环境地址、路径前缀和授权方式，`<ENV_API_TOKEN>` 使用该环境提供的授权凭据；入口要求其他认证头时按部署方说明替换，不使用本地模拟器凭据。

```http
POST /plugin/invoke
Content-Type: application/json
Authorization: Bearer <ENV_API_TOKEN>
Idempotency-Key: demo-001

{
  "pluginId": "exp_hello_backend",
  "handler": "example.create",
  "input": { "record_key": "demo-1", "title": "第一条记录" }
}
```

前端通过 `ctx.apiCall` 调用（网关自动处理 token 和前缀），写法见 [HTTP、WebSocket 与事件](../10.frontend/70.http-websocket-events.md)。本地接口调试使用[后端调试](../../40.debug-and-test/30.backend-debugging.md)的 HTTP 模拟器，错误码与正式网关存在差异。

## 错误处理：抛错时带上错误码

用 `throw { code, message }` 表达失败。**错误码 `code` 决定平台怎么处理这次错误**：

```ts
if (!recordKey) {
  throw { code: 'INVALID_ARGUMENT', message: 'record_key 不能为空' }
}
```

| 你抛的错误码（`code`） | 平台返回 | 含义 | 调用方该做什么 |
| --- | --- | --- | --- |
| `INVALID_ARGUMENT`、`UNKNOWN_FIELD`、`PERMISSION_DENIED` 等契约错 | HTTP 400 + `code: 40006` | 参数或寻址不合法，重试一万次也一样 | 改请求，不要重试 |
| `NOT_FOUND`、`DUPLICATE`、`CONFLICT` | HTTP 200 + `code: 20001` | 这是业务结果，不是故障 | 按业务逻辑处理 |
| 其他错误码（或不抛 `code`） | HTTP 503 + `code: 50301` | 系统抖动，可能重试就好 | 用同样的幂等键退避重试 |

响应信封固定为 `{code, message, data}`，成功判据是 `HTTP 2xx && code === 0`。失败时响应里没有 `data` 键。

以上数字码描述已部署网关契约；当前本地网关也返回数字分类，但 HTTP 状态、顶层字段校验等差异见[后端调试](../../40.debug-and-test/30.backend-debugging.md#已知限制)。HTTP 接口处理函数不自动提升返回的失败信封，`store` 失败需要使调用失败时应显式 `throw result.error`。

## 幂等

- 调用方在请求头带 `Idempotency-Key`，脚本里通过 `ctx.idempotencyKey` 拿到，用 `ctx.stableId(scope)` 可以派生稳定的业务 ID。
- 本地/网关层会把同一幂等键的重复请求缓存响应（重试拿到第一次的结果）；**真正的业务幂等要靠数据层**：`store.createIfAbsent`（唯一键去重）或带条件的 `store.update`（影响行数判断）。
- 用了 `ctx.stableId()` 却没带幂等键，会直接得到契约错误——平台不会替你生成随机值。
- 经验法则：**写操作传业务稳定键，读操作不传**。

## 超时与限制

| 项 | 值 |
| --- | --- |
| 单次执行超时 | 5 秒 |
| 请求体上限 | 1 MiB |
| 可用能力 | 按清单 `allowlist` 注入全局对象 |

5 秒内做不完的事（视频处理、批量计算、等用户操作）不要放在 HTTP 接口里——用[流程编排](./60.workflow.md)或[消息订阅](./30.event-handler.md)。

## 完整示例

模板自带一个带幂等创建的完整链路（HTTP 入口 → `shared/` 业务 → `store`），见[第一个后端插件](../40.hands-on/30.first-backend-plugin.md)第 3 节。业务逻辑放 `shared/`、入口只做接线，是模板刻意示范的结构——HTTP、事件、流程三种入口会共用同一份逻辑。

## 安全提醒

- 请求里的 `project_id`、`dock_sn` 等业务参数**可以伪造**，平台不提供"当前登录用户是谁"的可信上下文。涉及归属和权限的判断要在业务层做。
- 不要查全表后整条返回；库新加的列会被一起带出去。明确挑选返回字段。
- 签名 URL、token、原始配置不要写进返回值、错误信息和日志。

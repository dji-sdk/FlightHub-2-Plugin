# 多宿主插件

同一个插件可以同时出现在驾驶舱、项目、计划、消息四个页面。这一页讲多宿主插件的运行规则：每个页面各自怎么激活、代码怎么组织、哪些东西能共享哪些不能。

## 前置条件

- 已理解单宿主的入口/界面分层（见[入口与生命周期](./30.entry-and-lifecycle.md)）。
- 清单里已为每个目标宿主声明了对应的扩展。
- 已跑过 `pnpm run generate`，拿到各宿主的 `App*Context` 类型。

> `fh2-plugin-sdk` 是插件开发 SDK；下文模块名用于说明，实际导入路径保留生成工程配置。模块名不表示已发布的 npm 包名。

## 四个宿主，各自独立运行

宿主固定为 4 个：`cockpit`、`plan`、`message`、`project`。主应用不是宿主，但驾驶舱宿主就运行在主应用内。

| 宿主 | 扩展点 | 运行方式 |
| --- | --- | --- |
| `cockpit` | 8 个 `cockpit.ui.*`（工具栏、菜单栏、直播浮层、面板等） | `isolated-realm` |
| `plan` | `plan.form-extensions` | `isolated-iframe` |
| `project` | `project.sidebar-actions` | `isolated-iframe` |
| `message` | `message.alert-popups` | `isolated-iframe` |

表中的运行方式由宿主决定，插件作者不能通过清单或代码切换。

关键规则：**一个插件 ID 在每个宿主里是独立的运行时**。各自有一份 `ctx`、各自的 `ctx.host.instanceId`、各自的状态、资源和生命周期。它们不共享内存变量，也没有激活顺序保证——不能假设 A 页面先激活、B 页面就能读到 A 的数据。

扩展点契约的完整清单见[扩展点目录](../../70.api-reference/10.frontend/30.extension-point-catalog.md)。

## 入口只写一份，按宿主分流

```ts
// src/plugin.ts（节选）
export default definePlugin({
  async activate (ctx: PluginContext) {
    switch (ctx.host.id) {
      case 'cockpit':
        return (await import('./hosts/cockpit/activate')).activate(ctx as AppCockpitContext)
      case 'project':
        return (await import('./hosts/project/activate')).activate(ctx as AppProjectContext)
      case 'message':
        return (await import('./hosts/message/activate')).activate(ctx as AppMessageContext)
      case 'plan':
        return (await import('./hosts/plan/activate')).activate(ctx as AppPlanContext)
      default:
        return undefined
    }
  },
})
```

- 只为清单实际声明的宿主保留分支。没有计划页扩展就不写 `plan` 分支。
- 每个宿主的激活逻辑放独立的 `src/hosts/<host>/activate.ts`，互不 import。

## 代码放哪里共享

| 想共享的东西 | 放哪里 |
| --- | --- |
| 数据结构、校验、格式化、`ctx.apiCall()` 请求封装 | `src/shared/` |
| 同一插件各宿主间的内存态协作 | `src/services/`（跨宿主通信服务契约，见下文） |
| 跨用户、跨刷新、需要留痕的权威数据 | 后端（见[后端工程结构](../20.backend/00.package-structure.md)） |

明确不允许的两种做法：

- 从 `hosts/project/activate.ts` 导入消息或驾驶舱的宿主激活模块：运行时各自独立，这种 import 只会带来意外耦合。
- 把 `ctx.storage` 当跨宿主实时总线——它是本机缓存，没有跨宿主通知机制。

同一插件 ID 的两个宿主运行时之间需要短期同步状态时，用跨宿主通信服务：一个宿主提供实现，其他宿主连接调用，写法见[跨宿主通信服务](./60.plugin-service.md)。

## 能力按宿主可用

每个宿主提供的能力不同：`cockpit:*` 只有驾驶舱有，`project:context` 只有项目页有。所以每段宿主激活代码都按"取能力 → 判 `undefined` → 降级"的模板写：

```ts
// src/hosts/project/activate.ts（节选）
const project = await ctx.capabilities.get('project:context')
if (!project) return // 项目页之外不会走到这里，但缺席分支必须写
```

不要把 A 宿主拿到的能力句柄传给 B 宿主的代码用。各宿主的能力可用性见[能力可用性](../../30.features/70.capability-availability.md)。

## 日常命令与预期

```bash
pnpm run generate
pnpm run validate
pnpm run build
pnpm run dev
```

预期：本地调试页面里每个宿主只显示属于它的扩展；单独卸载一个宿主不影响其他宿主的运行时。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| TypeScript 报宿主上下文不匹配 | 清单里的扩展点改了但没重新生成类型；跑 `pnpm run generate` |
| 某个能力是 `undefined` | 当前宿主不提供这个能力；按该宿主的可用能力做降级，不要跨宿主复用句柄 |
| A 页面写入的变量 B 页面读不到 | 正常：运行时不共享内存。短期协作走跨宿主通信服务，持久数据放后端 |
| `switch` 里写了不认识的页面名 | 合法宿主 ID 只有 `cockpit`、`plan`、`message`、`project` |
| 一个页面操作后另一个页面没反应 | 两个宿主间没有事件互通；用跨宿主通信服务的事件或后端推送同步 |

# 跨宿主通信服务

跨宿主通信服务解决一个具体问题：**同一个插件的多个宿主运行时之间，怎么共享内存里的状态**。比如驾驶舱侧记录了"当前派遣的任务"，项目页想知道——它们是两份独立运行时，不能直接读对方的变量，这时由一方提供跨宿主通信服务，另一方连接调用。

它只适合短期、内存态的协作。跨用户、跨刷新、需要留痕的数据请放后端。

## 前置条件

- 至少两个宿主会激活同一个插件 ID。
- 需要的是实时协作，不是持久化存储。

> `fh2-plugin-sdk` 是插件开发 SDK；下文模块名用于说明，实际导入路径保留生成工程配置。模块名不表示已发布的 npm 包名。

## 第一步：定义契约

契约放在双方都能 import 的共享模块里（推荐 `src/services/`）：

```ts
// src/services/dispatch.ts
import { definePluginService } from 'fh2-plugin-sdk'

export interface DispatchSnapshot {
  readonly activeId: string | null
  readonly status: 'idle' | 'pending'
}

export interface DispatchMethods {
  getSnapshot: () => DispatchSnapshot
  present: (input: { readonly id: string }) => { readonly accepted: boolean }
}

export interface DispatchEvents {
  readonly changed: DispatchSnapshot
}

export const dispatchService = definePluginService<DispatchMethods, DispatchEvents>('dispatch')
```

契约校验规则（违反了编译期直接报错）：

- 方法最多一个参数，参数、返回值、事件 payload 都必须是可跨边界传输的值。
- 方法名不能用 `dispose` 和 `on`。
- 方法名和事件名不能重名。

## 第二步：一个宿主提供实现

```ts
// src/hosts/cockpit/activate.ts（节选）
const listeners = new Set<(snapshot: DispatchSnapshot) => void>()
let snapshot: DispatchSnapshot = { activeId: null, status: 'idle' }

await ctx.services.provide(dispatchService, {
  getSnapshot: () => snapshot,
  present: ({ id }) => {
    snapshot = { activeId: id, status: 'pending' }
    for (const listener of listeners) listener(snapshot)
    return { accepted: true }
  },
  // 事件成员：宿主连接时注册回调，返回的 Disposable 负责注销
  changed: (emit, options) => {
    listeners.add(emit)
    if (options?.immediate) emit(snapshot)
    return { dispose: () => listeners.delete(emit) }
  },
})
```

同一个跨宿主通信服务 ID 同时只应有一个提供方。服务提供方的注册随当前运行时停止自动回收，不需要手动注销。

## 第三步：其他宿主连接使用

```ts
// src/hosts/project/activate.ts（节选）
const client = await ctx.services.connect(dispatchService)

const subscription = await client.on('changed', snapshot => {
  ctx.logger.info('派遣状态变化', snapshot)
})

try {
  const current = await client.getSnapshot()
  ctx.logger.info('当前派遣状态', current)
} catch (error) {
  ctx.logger.warn('派遣服务当前不可用', {
    message: error instanceof Error ? error.message : String(error),
  })
}
```

连接后拿到 client：方法调用全部返回 Promise；`client.on(事件名, 回调)` 订阅事件。提前不需要时可以 `client.dispose()` 或 `subscription.dispose()`。

## 没有先后顺序保证

不同宿主的激活顺序是不确定的。服务提供方可能还没激活，服务调用方就已经 `connect` 了。所以：

- 调用失败（比如 `SERVICE_UNAVAILABLE`，表示当前没有可用的提供方）是**正常分支**，要提示用户重试或降级，不要当成 bug。
- 不要用轮询 `connect()` 的方式"等"另一个宿主先激活——这解决不了顺序问题，还制造无谓的流量。

## 日常命令与预期

```bash
pnpm run tsc
pnpm run test
pnpm run build
pnpm run dev
```

预期：服务提供方宿主激活后，服务调用方宿主的方法和事件都能工作；服务提供方宿主卸载后，服务调用方不再把旧状态当作有效数据，而是进入"服务不可用"分支。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 报 `SERVICE_UNAVAILABLE` | 当前没有已激活的服务提供方；处理该分支（提示重试/降级），不要跨宿主 import 函数 |
| 契约类型编译不过 | 方法参数超过一个、或传了不可序列化的值（函数、DOM 等）；改成普通数据结构 |
| 方法名或事件名报错 | 方法不能用 `dispose`/`on`，方法与事件不能重名 |
| 服务提供方卸载后服务调用方拿到旧值 | 正常：连接断开后旧状态不再有效，业务上要重新拉取或等待重试 |
| 想跨插件调用别的插件的跨宿主通信服务 | 不支持；跨宿主通信服务只在同一个插件 ID 内部使用 |
| 状态重启后丢了 | 跨宿主通信服务是内存态；需要持久化就写后端 |

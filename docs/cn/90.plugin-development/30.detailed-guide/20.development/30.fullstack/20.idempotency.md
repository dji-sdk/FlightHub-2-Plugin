# 端到端幂等

网络重试、消息重投、流程重放，都会让同一个操作被执行多次。写操作不去重，就会产生重复数据、重复下发任务。这一页讲每条链路靠什么去重，读完你能安全地写出"创建记录、推进状态"这类接口。

## 为什么会重复执行

至少有三个来源：

1. 前端网络超时后重试同一个请求。
2. 事件消息是"至少一次"投递，消费方可能收到重复消息。
3. 平台按幂等键重放流程步骤。

所以后端接口不能假设"每个请求只来一次"，要用幂等原语保证"来多少次结果都一样"。

## 每条链路的去重原语

| 链路 | 平台提供什么 | 你要做的事 |
|---|---|---|
| HTTP 接口 | `Idempotency-Key` 头 → `ctx.idempotencyKey` | 用 `ctx.stableId(scope)` 或业务唯一键写库 |
| 数据新建 | `store.createIfAbsent` + 唯一键 | 设计业务唯一键，按 `created` 区分新建/已存在 |
| 状态推进 | `store.update` 返回 `affected` | update 带旧状态条件，`affected === 1` 才算抢占成功 |
| 流程启动 | `flow.start(流程名, bizId)` → `workflowId = 流程名 + "-" + bizId` | 所有入口用同一个稳定 `bizId`，重复启动返回 `already` |
| 流程步骤 | 幂等键 `workflowID:stepID`，脚本里可读 `run.idempotencyKey` | 有外部副作用的步骤，把这个键透传给下游 |
| 事件消费 | 消息的 `event_id` 注入 `ctx.idempotencyKey` | 副作用全部幂等：唯一键去重、条件更新 |

一个关键函数：`ctx.stableId(scope)` 用幂等键 + scope 派生稳定 ID（同一请求多次调用结果相同）。请求没带幂等键时它直接抛契约错——平台不会生成随机值兜底，所以关键写操作一定要让调用方带 `Idempotency-Key`。

## 前端：生成并保存业务键

幂等键要能跨重试保持不变，所以在发起请求**之前**生成，存在本地状态里：

```ts
// 业务键来自业务事实（谁、何时、对什么），不是随机数
const eventKey = `${crossedAt}:${objId}:${regionId}`

// 首次调用
await invoke(ctx, pluginId, 'lane-change.create-event', input, {
  idempotencyKey: `lane-change:${eventKey}`,
})

// 网络失败重试：复用同一个键，不要重新生成
await invoke(ctx, pluginId, 'lane-change.create-event', input, {
  idempotencyKey: `lane-change:${eventKey}`,
})
```

读操作（查询列表、查详情）不需要幂等键。

## 后端：用唯一键做原子创建

创建类接口用 `store.createIfAbsent`，唯一键冲突时返回已有记录而不是报错：

```ts
// handlers/lane-change/create-event.ts
export function handle (input: RecordInput, ctx: HandlerCtx) {
  const saved = store.createIfAbsent('lane_change_event', {
    event_key: input.event_key,
    project_id: input.project_id,
    post_status: 'pending_video'
  }, ['event_key'])            // uniqueBy：按这些字段判重

  if (!saved.ok) {
    throw saved.error
  }
  return {
    event_id: saved.data.record.id,
    created: saved.data.created   // true = 本次新建；false = 已有同 key 记录
  }
}
```

创建和更新时间由平台维护，不要在 `createIfAbsent` 的记录参数中写 `created_at` / `updated_at`。SQL 物理列名仍为 `created_at` / `updated_at`；JS `store` 返回及筛选/排序使用公开名 `createdAt` / `updatedAt`，例如读取 `saved.data.record.createdAt`，不能直接把物理列名当作脚本字段。

两个要点：

- `created` 是 `true` 还是 `false` 都是成功（`code=0`）。前端按 `event_id` 继续流程，不要把 `created=false` 当失败。
- 数据库侧要有唯一索引兜底，写在插件的 `schema.sql` 里（生产建表用它，平台不会自动执行）：

```sql
-- schema.sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_lane_change_event_key
  ON plugin_db_lane_change_event (event_key);
```

## 状态推进：条件更新

推进状态时把"旧状态"写进更新条件。别人抢先改过状态，`affected` 就是 0：

```ts
const updated = store.update('lane_change_event', {
  id: { eq: eventId },
  post_status: { eq: 'pending_video' }   // 只允许从 pending_video 推进
}, {
  post_status: 'waiting_artifacts',
  video_file_id: fileId
})
if (!updated.ok) {
  throw updated.error
}
```

`affected === 0` 不证明作业已启动：可能是上次"已绑视频、还没启动流程"时进程中断了。需要 `data:read` 查询目标记录，确认仍为 `waiting_artifacts` 且 `video_file_id` 是同一个 `fileId` 后，继续用稳定流程名、`bizId` 和 `seed` 补启；记录不存在、已改绑或已推进状态则返回对象。不能一律提前返回，也不能不检查绑定就无条件启动。完整同绑定检查见[事件、通知与状态](./30.events-and-state.md)。

## 流程启动：确定性的 bizId

`flow.start(流程名, bizId)` 用 `bizId` 拼出流程实例 ID。所有会启动同一业务流程的入口（事件回调、手工补偿……）必须用同一个 `bizId`，才能命中同一个实例：

```ts
const started = flow.start('lane-change-postprocess', `${eventId}:${fileId}`, {
  event_id: eventId,
  video_file_id: fileId
})
// 同一个 bizId 再启动得到 already === true：这段视频的作业已经在跑
```

`bizId` 要带上视频维度。同一事件可能先等到一段不含违法时刻的视频，后处理退回等下一段；只用 `eventId` 会撞上已经结束的流程 ID，新视频就再也起不来了。

本例的两键调用要求目标声明为 `"job":{"seed":["event_id","video_file_id"]}`；与其他页面含 `video_object_key` 的三键片段示例不是可直接拼装的完整组合，传入键必须与实际 `job` 声明完全相同。

流程里有对外副作用的步骤（比如推送结果），把平台给的幂等键显式传下去：

```json
{
  "inputs": {
    "script": { "const": "push-result" },
    "eventId": { "from": "trigger.eventId" },
    "idempotencyKey": { "from": "run.idempotencyKey" }
  }
}
```

一步要发多条记录时，用稳定顺序加序号生成子键，不要用对象遍历顺序、墙钟或随机数：

```ts
for (const i = 0; i < input.items.length; i++) {
  pushOne(input.items[i], input.idempotencyKey + ':' + i)
}
```

## 没有跨存储的事务

当前平台没有"改数据库 + 启动流程 + 发通知"在一个事务里完成的能力。典型窗口：

```text
写业务状态成功
  ↓ 进程在这里崩溃
flow.start / notify.publish 还没执行
```

补救方式是：让重复投递的消息再次执行，用同绑定查询检查补启并复用确定性 `bizId`，而不是因 `affected === 0` 提前确认消息。这个检查需要 `data:read`，只确认可补偿的业务状态，不代替 `affected` 判断谁抢到了更新。查询与启动仍不是原子操作，不能消除后续并发改绑或取消的窗口。

查询或启动持续失败会耗尽有界重试并丢弃消息（`Discard`）；依赖恢复后可人工重放死信消息补启，**没有自动死信恢复保证**。死信保存也依赖队列配置；要保证长期最终恢复需另行设计对账或事务发件箱。不要假设"代码紧挨着写"就是原子的。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 调 `ctx.stableId` 报契约错误 | 请求没带 `Idempotency-Key` 头；让调用方补上 |
| 重复提交出现两条记录 | 唯一键没设计对，或 `schema.sql` 里的唯一索引没建 |
| `created=false` 被当前端失败 | 它是"已存在"的正常结果，按 `event_id` 继续 |
| 重试后数据重复 | 重试时换了幂等键；键必须在首次请求前生成并复用 |
| 状态被旧请求改回去 | update 条件里没带旧状态；补上 `status: {eq: ...}` 条件 |

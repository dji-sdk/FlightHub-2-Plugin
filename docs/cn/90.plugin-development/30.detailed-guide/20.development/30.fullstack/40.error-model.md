# 统一错误模型

接口出错时，平台按你抛出的 `code` 把错误分成三类，决定 HTTP 状态码、响应码和"该不该重试"。这一页讲三分类规则、前后端各自的写法，读完你能让前端正确区分"参数写错了""记录不存在""系统暂时不可用"。

## 抛错怎么写

后端脚本里用 `throw` 带 `code` 和 `message`：

```ts
throw { code: 'INVALID_ARGUMENT', message: 'title 不能为空' }
throw { code: 'NOT_FOUND', message: '记录不存在' }
```

平台按 `code` 分类：

| 类别 | 错误码（`code`） | 平台行为 | 你该怎么用 |
|---|---|---|---|
| 契约错误 | `INVALID_ARGUMENT` / `UNKNOWN_FIELD` / `UNKNOWN_ENTITY` / `INVALID_FILTER` / `EMPTY_FILTER` / `TYPE_MISMATCH` / `LIMIT_EXCEEDED` / `PERMISSION_DENIED` | HTTP 400 + `code=40006` | 参数缺失、格式不对；调用方改参数就能好，**不要重试** |
| 业务结果 | `NOT_FOUND` / `DUPLICATE` / `CONFLICT` | HTTP 200 + `code=20001` | 查无此记录、重复提交、状态冲突；这是正常业务结果，**不要重试** |
| 系统错误（默认档） | `TIMEOUT` / `UNAVAILABLE` / `DEADLOCK` / `STORAGE_ERROR`，以及一切认不出的 `code` | HTTP 503 + `code=50301` | 网络抖动、下游暂时不可用；调用方**可以退避重试** |

注意：拼错 `code`（比如写成 `NOTFOUND`）不会自动变成契约错误，而是落进默认档（可重试）。写完记得核对拼写。

## 一个完整的接口处理函数示例

```ts
// handlers/capture/get-event.ts
function requireText (input, key) {
  const value = String(input[key] == null ? '' : input[key]).trim()
  if (!value) {
    throw { code: 'INVALID_ARGUMENT', message: key + ' 不能为空' }
  }
  return value
}

export function handle (input: RecordInput, ctx: HandlerCtx) {
  const eventId = requireText(input, 'event_id')

  const result = store.query('capture_event', { id: { eq: eventId } }, { limit: 1 })
  if (!result.ok) {
    throw { code: result.error.code, message: '查询抓拍失败: ' + result.error.message }
  }
  if (result.data.list.length === 0) {
    throw { code: 'NOT_FOUND', message: '抓拍事件不存在' }
  }

  const row = result.data.list[0]
  return { event_id: row.id, status: row.status || '' }
}
```

不要这样写：

```ts
// ❌ 平台会把返回值当成成功，前端拿到 code=0
return { ok: false, error: '数据库失败' }
```

HTTP 接口处理函数和流程脚本不自动提升返回的失败信封，需要调用失败时必须显式 `throw result.error`。`store` 方法返回的 `{ ok: false, error }` 是底层约定，接口处理函数检查到后要转成 `throw`。事件入口顶层的失败信封则会按 `error.code` 分类消息处置，不能把事件规则套用到另外两路；三种入口都必须返回对象，无业务输出通常为 `{}`。

## HTTP 信封对照表

| HTTP | 响应码（`code`） | 含义 | 前端动作 |
|---:|---:|---|---|
| 200 | `0` | 成功 | 读 `data` |
| 200 | `20001` | 插件业务结果（NOT_FOUND/DUPLICATE/CONFLICT 等） | 显示业务提示，不自动重试 |
| 400 | `40001` | JSON 非法或 invoke 顶层字段多余 | 检查请求体 |
| 400 | `40006` | 插件契约错误 | 修正参数，不重试 |
| 401 | `40101` | 鉴权失败 | 重新登录 |
| 403 | `40301` | 流程未声明 `api` 触发器 | 检查流程 `trigger` 配置 |
| 404 | `40401` / `40402` | 流程 / 流程实例不存在 | 检查流程名和实例 ID |
| 409 | `40901`~`40903` | 流程信号时机、作用域或重复冲突 | 先刷新状态再决定 |
| 503 | `50301` | 插件系统错误 | 先核对错误及写入结果，安全重试须复用原幂等键 |
| 504 | `50401` | 信号投递超时，结果未知 | 先查实例状态，再决定是否重发同一信号 |

## 前端：结构化处理错误

`ctx.apiCall` 在网关业务码非零时直接抛 `PluginError`（稳定形状：`code`、`message`，网关业务码在 `detail.gatewayCode`）。用 SDK 的 `isPluginError` 做结构判断，不要依赖 `instanceof`：

> fh2-plugin-sdk 为文档使用的 SDK 模块名；实际路径使用生成工程配置。保留生成工程中的实际 import，不按文档模块名修改依赖或工具链别名。

```ts
// src/shared/invoke.ts
import { isPluginError } from 'fh2-plugin-sdk'
import type { JsonValue, PluginContext } from 'fh2-plugin-sdk'

interface GatewayDetail {
  readonly gatewayCode?: number
  readonly httpStatus?: number
  readonly gatewayMessage?: string
}

export async function invoke<T> (
  ctx: Pick<PluginContext, 'apiCall'>,
  pluginId: string,
  handler: string,
  input: Record<string, JsonValue>,
  idempotencyKey?: string,
): Promise<T> {
  try {
    const res = await ctx.apiCall<{ code: number; message: string; data: JsonValue }>('/plugin/invoke', {
      method: 'POST',
      body: { pluginId, handler, input },
      ...(idempotencyKey ? { idempotencyKey } : {}),
    })
    // 只有 code === 0 才会走到这里
    return res.data as T
  } catch (error) {
    if (isPluginError(error) && error.code === 'PLUGIN_GATEWAY_ERROR') {
      const detail = (error.detail ?? {}) as GatewayDetail
      // gatewayCode 对应上方对照表：40006 契约、20001 业务、50301 系统
      const gatewayCode = detail.gatewayCode ?? 0
      const retryable = gatewayCode === 50301 || gatewayCode === 50401
      const business = gatewayCode === 20001
      void retryable
      void business
      throw new Error(`[${gatewayCode}] ${detail.gatewayMessage ?? error.message}`)
    }
    throw error
  }
}
```

传输信封的 `data` 和请求 `input` 按 `JsonValue` 约束，不能把未约束的 `T` 直接传给 `apiCall`。封装返回的 `T` 是插件的业务契约，`as T` 不替代运行时字段校验；只需要 `apiCall` 的上下文即可调用。完整工程写法见[第一个全栈插件的调用封装](../40.hands-on/40.first-fullstack-plugin.md#_3-调用封装-src-shared-backend-ts-新建)。

数字码对照表描述已部署网关。当前 `1.0.0` 本地模拟网关已把后端错误转换为 `40006` / `20001` / `50301` 数字信封，原脚本错误码保留在错误文案中，不应再按字符串 `code` 处理。不过本地 HTTP 状态仍可能不同，例如业务 `NOT_FOUND` 的本地 HTTP 状态可以是 `404`；数字码分类不能证明目标网关全部行为一致，正式调用与前端展示仍须在目标环境验证。

重试原则：

- HTTP 失败后平台不会自动重发请求。`gatewayCode` 为 `50301` / `50401` 时，先查权威业务或流程状态；确认可以安全重试后，**复用原来的 `Idempotency-Key`**。稳定键还须配合后端原子去重，不能单凭请求头保证没有重复副作用。
- `40006`、业务 `20001`、`409xx` 不要盲目自动重试；`409xx` 先刷新业务/流程状态再决定。
- 对最终用户展示时，系统错误的消息不一定友好，显示稳定的"稍后重试"提示并记录 `gatewayCode` 即可。

## 数据存储的错误

`store` 方法不抛错，返回稳定的错误对象：

```json
{
  "ok": false,
  "error": { "code": "INVALID_FILTER", "message": "筛选条件非法" }
}
```

- 表不存在、列不存在、缺唯一索引等数据库问题，对脚本统一收敛为 `STORAGE_ERROR`（可重试档）；细节只在服务日志里。
- 空查询结果**不是** `NOT_FOUND`，返回 `{ list: [], total: 0 }`。要不要翻成业务 `NOT_FOUND` 由接口处理函数决定。

## 事件与流程里的处置差异

同一个 `NOT_FOUND`，在不同链路里的处置不同：

| 链路 | 处置 |
|---|---|
| HTTP 调用 | 返回 `200/20001`，由前端展示 |
| 流程步骤 | 业务结果让步骤失败，不重试；系统错误按该动作和步骤的有效策略处理 |
| 事件消费 | 确认消费，不重投 |

错误"类别"是稳定的，但各链路对它的"处置"不同。写事件脚本时要清楚这一点：把业务结果误抛成系统错误，会导致消息被反复重投。

最大尝试次数包含首次执行：默认 `5` 次尝试最多产生 `4` 次重试，不是重试 `5` 次。非幂等受控动作保持单次尝试，`run_script` 重试会重新执行整段脚本；动作退避、显式调整和导出差异统一见[重试边界](../../70.api-reference/20.backend/60.workflow-dsl.md#重试边界)。事件则按每次投递的部署配置尝试，不套用流程默认值。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 前端拿到 503 反复重试 | 接口处理函数抛了认不出的 `code`（如拼写错误）；核对三分类表 |
| `DUPLICATE` 被当故障弹窗 | 它是业务结果（200/20001）；重复本该正常的链路改用 `createIfAbsent` |
| 接口处理函数返回 `{ok:false}` 前端却显示成功 | HTTP 接口处理函数不提升失败信封，需要失败时显式 `throw result.error` |
| 空列表报"记录不存在" | 空结果要自己判断后转 `NOT_FOUND`，平台不会替你转 |
| 错误信息里出现敏感数据 | 错误消息会到客户端和日志；只放字段名和原因，不放请求体、token、SQL |

# 前后端共享契约

前后端是两个独立的插件，靠一份接口约定对上：前端按约定发请求，后端按约定校验和返回。这一页讲两件事——前端怎么调后端（入口、响应、异常），以及双方怎么约定字段。

> 文中 `fh2-plugin-sdk` 是文档里的模块名，实际导入路径以生成工程为准；不要照文档改依赖或工具链别名。

## 固定调用入口

前端调用后端只有一个入口，靠 `handler` 名字区分接口：

```text
前端 ctx.apiCall('/plugin/invoke', { method: 'POST', body: { pluginId, handler, input } })
        │
        ▼
插件网关（自动带 token，自动加 /plugin-api 前缀）
        │
        ▼
后端 POST /plugin/invoke → 按 (pluginId, handler) 找到 handle(input, ctx) 执行
```

- 请求体顶层只接受 `pluginId / handler / input` 三个字段，多写返回 `40001`。
- `input` 平台不校验、不裁剪，原样交给 `handle(input, ctx)`；参数校验是后端插件自己的事。
- 后端返回值必须是对象，原样放进响应的 `data`。
- 请求体 `body` 支持 JSON、Blob（不超过 10MB）或受控分段表单；GET 请求不能带请求体。

## 响应信封与成功判据

响应永远是 `{ code, message, data }` 信封：

```json
{ "code": 0, "message": "success", "data": { "event_id": "evt-001" } }
```

- 失败不走返回值：网关业务码非零时 `ctx.apiCall` 直接抛 `PluginError`，只有成功请求才返回完整信封。
- 抛出的错误 `code` 是 `PLUGIN_GATEWAY_ERROR`，网关业务码在 `error.detail.gatewayCode`。
- 失败响应没有 `data` 键，只有 `code` 和 `message`。
- 业务结论（比如"记录不存在"）用 HTTP 200 + `code=20001` 表达，平台同样当异常抛出来。前端统一在 catch 里处理，靠 `gatewayCode` 区分是参数错了、业务结论还是系统故障。

前端统一封装一份，整个工程共用。封装的具体形状不唯一（加不加 pluginId 参数、怎么传幂等键都可以），重要的是两点：**失败统一在异常分支处理**、**写操作带业务稳定的幂等键**：

```ts
// src/shared/backend.ts
import { isPluginError } from 'fh2-plugin-sdk'
import type { JsonValue, PluginContext } from 'fh2-plugin-sdk'

export async function invoke<T> (
  ctx: Pick<PluginContext, 'apiCall'>,
  pluginId: string,
  handler: string,
  input: Record<string, JsonValue>,
  options: { idempotencyKey?: string; timeoutMs?: number } = {},
): Promise<T> {
  try {
    const res = await ctx.apiCall<{ code: number; message: string; data: JsonValue }>('/plugin/invoke', {
      method: 'POST',
      body: { pluginId, handler, input },
      ...(options.idempotencyKey ? { idempotencyKey: options.idempotencyKey } : {}),
      ...(options.timeoutMs ? { timeoutMs: options.timeoutMs } : {}),
    })
    // 只有 code === 0 才会走到这里
    return res.data as T
  } catch (error) {
    if (isPluginError(error)) {
      // 网关业务码非零（40006 参数错误、20001 业务结果、50301 系统错误等）统一在这里转成可读错误
      throw new Error(`invoke 失败: ${error.code} ${error.message}`)
    }
    throw error
  }
}
```

`apiCall` 的请求和响应都只能是 JSON 数据。代码里的 `T` 是你自己标注的业务结果类型，`as T` 不做运行时校验，字段合不合法要在后端判。要完整接线时，使用[第一个全栈插件的调用封装](../40.hands-on/40.first-fullstack-plugin.md#_3-调用封装-src-shared-backend-ts-新建)。

当前本地网关返回数字分类，可核对 `detail.gatewayCode` 与字段错误；本地 HTTP 状态、对象排序和媒体消息包装仍与目标环境存在差异。边界见[后端调试的已知限制](../../40.debug-and-test/30.backend-debugging.md#已知限制)，目标信封与媒体链路在已部署测试环境另验。

注意：

- 接口路径写 `/plugin/invoke`，不要自己加 `/plugin-api` 前缀或写完整网址，网关负责。
- 插件入口中的裸 `fetch` / `XMLHttpRequest` 会被网络护栏拦截，应通过 `ctx.apiCall` 发 HTTP。界面在宿主同一 JavaScript 运行域执行，不安装入口护栏；作者仍应把业务网络调用留在入口，不用界面绕过受管通道。
- 写操作（创建、更新、删除）建议带 `idempotencyKey`，见[端到端幂等](./20.idempotency.md)。

## 一份字段契约长什么样

用交通抓拍"创建变道事件"接口举例。接口名由后端文件路径加命名导出得来（`handlers/lane-change/create-event.ts` + `export function createEvent` → `lane-change.create-event`）。

请求 `input` 的类型：

```ts
export interface CreateLaneChangeEventInput {
  project_id: string
  dock_sn: string
  flight_id: string
  event_key: string          // 业务唯一键：<crossed_at>:<obj_id>:<region_id>
  crossed_at: number         // UTC 毫秒时间戳
  collision_type: 'solid_line' | 'guide_area'
  obj_id: string
  region_id: string
  annotation_id?: string
  annotation_snapshot: {
    name?: string
    kind: 'line' | 'polygon'
    normalized_points: Array<{ x: number; y: number }>  // 坐标范围 [0,1]
    geo_points?: Array<{ lat: number; lng: number }>
  }
}
```

响应 `data` 的类型：

```ts
export interface CreateLaneChangeEventOutput {
  event_id: string
  event_key: string
  post_status: string
  createdAt: string
  created: boolean           // false = 已有同 key 记录，不是失败
}
```

后端拿同一份类型写实现，只做平台不做的事——校验、幂等、错误码：

```ts
// handlers/lane-change/create-event.ts
export function createEvent (
  input: CreateLaneChangeEventInput,
  ctx: HandlerCtx,
): CreateLaneChangeEventOutput {
  const key = String(input.event_key ?? '').trim()
  if (!key) throw { code: 'INVALID_ARGUMENT', message: 'event_key 不能为空' }  // → 前端收到 400 / 40006
  // 按 event_key 幂等写入，见“数据存储”
  return { event_id, event_key: key, post_status, createdAt, created }
}
```

后端的校验可以比类型更严（示例包的做法）：

- 字符串必填且去除首尾空白后非空。
- 枚举字段只接受列出的值。
- 时间戳必须是正的毫秒数，不超过 13 位。
- `normalized_points` 非空且坐标在 `[0,1]`；整个快照序列化后不超过 32768 字符。

这份类型建议放在前后端都看得到的地方（比如前端工程 `src/shared/contracts.ts`），后端用注释或契约测试对齐。当前平台不会从清单自动生成接口数据结构，契约要靠人来维护。

## 字段与空值约定

| 约定 | 说明 |
|---|---|
| 业务 ID 用 string | 跨端传递不会被精度截断 |
| 时间用 UTC 毫秒 number | 后端按定宽 13 位字符串存储以便排序，边界处转换 |
| 空列表返回 `[]` | 不要返回 `null` 或 `undefined` |
| 空字符串状态返回 `""` | 没有值就用空字符串，别用 `null` |
| 返回值显式构造 | 后端只返回前端需要的字段，不要把存储行原样抛出 |
| 签名 URL 不入库 | 签名 URL 会过期，只用于展示，不进持久化数据和幂等键 |

## 调用身份与版本

1. 寻址只靠 `pluginId + handler`。接口名来自后端文件路径，改文件路径等于改接口名。
2. 后端清单的 `version` 是整包发布/回滚单位；调用响应不带回版本号，前端不要依赖。
3. 清单里的 `contractsRange` 只检查插件与平台运行时的兼容性，不约束你的业务字段。

## 改字段的顺序

先发布"新旧输入都能处理"的后端 → 前端切到新字段 → 再删旧字段。平台不会自动做字段协商，顺序错了旧前端会直接报错。

读操作不需要幂等键；写操作重试必须复用同一个业务幂等键，见[端到端幂等](./20.idempotency.md)。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 返回 `40001` | 请求体顶层多了字段，只保留 `pluginId/handler/input` |
| 返回 `40006` | 接口名拼错或插件未装载；名字 = 文件路径 + 命名导出（`handlers/a/b.ts` + `export function b` → `a.b`） |
| 界面显示 `[object Object]` | 把整个信封当数据用了；成功响应的业务数据在 `data` 字段，取它 |
| "查无此记录"被当成系统故障 | 业务结果走 `200/20001`，前端按错误码分类展示，见[统一错误模型](./40.error-model.md) |

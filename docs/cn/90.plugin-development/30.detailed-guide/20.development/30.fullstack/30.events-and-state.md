# 事件、通知与状态

后端发生了业务变化（媒体生成、事件状态变化），前端怎么知道？这一页讲可用的三条链路加一个旁路通知，以及最重要的一条原则：**权威状态永远以查询接口为准，通知只是提醒**。

## 三条链路怎么选

| 链路 | 输入 | 做什么 | 特点 |
|---|---|---|---|
| 插件事件（`events/`） | 平台媒体消息 | 执行一段事件脚本，可再 `flow.start` 启动流程 | 至少一次投递，脚本必须幂等 |
| 流程触发（`trigger.stream`） | 统一事件模型的事件流 | 按 `match` 命中后启动流程 | 启动失败不确认，可重投 |
| 前端轮询 | 前端定时调查询接口 | 读取业务当前状态 | 简单可靠，权威状态来源 |

另有一个旁路：`notify.publish` 把业务变化尽力推给前端（走 WebSocket）。它**不改变**权威状态，只用来加速界面刷新。

## 插件事件：媒体生成时触发

平台事件类型目前有两种：`media.photo_created` 和 `media.video_created`（平台指定，开发者不可改）。在清单里订阅，脚本放在 `events/` 目录：

```json
{
  "events": [
    {
      "type": "media.video_created",
      "consumer": [ { "handler": "events/video-created.ts", "entry": "onVideoCreated" } ]
    }
  ]
}
```

消费脚本做两件事：条件绑定媒体，然后启动后处理流程。下面是补偿逻辑的简化输入示例：`target_event_id` 表示本例已完成业务关联的目标记录 ID，不是承诺真实媒体消息自带该字段；真实消息形状与关联规则必须单独对账。本例需申报 `data:read`、`data:write`、`flow:start`：

```ts
// events/video-created.ts
export function onVideoCreated (input, ctx) {
  const eventId = String(input.target_event_id || '').trim()
  const fileId = String(input.file_id || '').trim()
  if (!eventId || !fileId) {
    // 缺字段是契约错误 → 消息进死信，不会重投
    throw { code: 'INVALID_ARGUMENT', message: 'target_event_id 和 file_id 不能为空' }
  }

  // 条件更新：只把 pending_video 状态的事件推进，天然防重
  const moved = store.update('lane_change_event', {
    id: { eq: eventId },
    post_status: { eq: 'pending_video' }
  }, {
    video_file_id: fileId,
    post_status: 'waiting_artifacts'
  })
  if (!moved.ok) {
    throw moved.error
  }
  if (moved.data.affected === 0) {
    const current = store.query('lane_change_event', { id: { eq: eventId } }, { limit: 1 })
    if (!current.ok) throw current.error
    const saved = current.data.list[0]
    if (!saved || saved.post_status !== 'waiting_artifacts' || saved.video_file_id !== fileId) {
      return { bound: false }
    }
  }

  const started = flow.start('lane-change-postprocess', `${eventId}:${fileId}`, {
    event_id: eventId,
    video_file_id: fileId
  })
  return { bound: moved.data.affected === 1, already: started.already }
}
```

`affected === 0` 不证明作业已启动：上一次可能更新成功却在启动时失败。本例只在记录仍为 `waiting_artifacts` 且绑定同一 `fileId` 时补启；不存在、已改绑或已推进状态则返回对象。`bound` 只表示本次是否新增绑定，补启始终复用同一个流程名、`bizId` 和 seed。

本例传两个 seed 键，所引用 job 的声明必须相同：

```json
{ "trigger": { "job": { "seed": ["event_id", "video_file_id"] } } }
```

这是 `job` 触发段，不是完整流程定义。[作业、目标轨迹与视频处理](../../30.features/60.backend-capabilities/80.job-trajectory-video.md)中的三键片段示例不能直接接收本例的两键调用。

查询或启动持续失败时仍会耗尽有界重试并丢弃消息（`Discard`）；依赖恢复后的人工重放可以补启，不能承诺自动死信恢复。查询与启动之间仍非原子，见[端到端幂等](./20.idempotency.md)。

消息投递是"至少一次"，后端运行时中命中的消费方并发执行、各自独立重试，全部结束后按 **Requeue > Discard > Ack**（重新入队 > 丢弃 > 确认）聚合一条消息的处置。业务依赖应放在同一个消费函数内调用或显式流程编排，本地模拟器不用于证明这些并发与处置语义；需在已部署测试环境验证，队列投递与重放方式由部署方提供。

入口必须返回对象，通常为 `{}`；事件入口顶层返回失败信封会按 `error.code` 分类，非对象返回是可重试错误。HTTP 接口处理函数和流程脚本不自动提升返回的失败信封，需要失败时须显式 `throw result.error`。单个消费方的处置规则：

- 业务结果（`NOT_FOUND` 等）：确认消费，不重投。
- 契约错误（`INVALID_ARGUMENT` 等）：丢弃（`Discard`），不重投；已配置死信保存时进入死信队列。
- 其他错误或非对象返回：按部署的 `MaxAttempts` 有界重试，耗尽后丢弃（`Discard`）；配置了死信交换机才进入死信队列。

所以脚本里的所有副作用都必须幂等，见[端到端幂等](./20.idempotency.md)。

本地模拟器的媒体输入包装与真实消息有差异，不能仅靠 `/mock/backend/event` 证明完整媒体消费链路；保持生产消息形状，不增加双形状兜底，见[已知限制](../../40.debug-and-test/30.backend-debugging.md#已知限制)。

## 前端：轮询查询接口

业务状态存在后端数据存储里，前端要看最新状态就调查询接口。典型的"等到终态为止"轮询：

```ts
type PostStatus = 'pending_video' | 'waiting_artifacts' | 'processing'
  | 'verified' | 'rejected' | 'failed'

const terminal = new Set<PostStatus>(['verified', 'rejected', 'failed'])

export async function waitResult (ctx: PluginContext, eventId: string) {
  for (let attempt = 0; attempt < 60; attempt++) {
    const detail = await invoke<{ post_status: PostStatus }>(
      ctx, pluginId, 'lane-change.get-event', { event_id: eventId },
    )
    if (terminal.has(detail.post_status)) return detail
    await sleep(2000)
  }
  throw new Error('等待处理结果超时，请稍后刷新')
}
```

两个要点：

- 轮询超时只是前端不再等了，后端状态还在正常推进，不要把它当成失败写回后端。
- 终态里 `rejected` 是确定的业务结论（审核不通过），`failed` 才是处理失败，界面提示要区分。

## 业务状态与流程状态是两回事

以变道抓拍为例，业务状态存在数据表里：

```text
pending_video → waiting_artifacts → processing → verified | rejected | failed
```

而流程实例有自己的执行状态（当前跑到了哪一步、在等什么信号）。前端业务页面只认查询接口返回的业务状态；流程状态只用于排障，或展示"当前在等哪个人工动作"。

## 通知：尽力而为的提醒

后端处理完可以发一条通知，前端订阅到后刷新界面：

```ts
// 后端函数内片段（三路均按 notify:publish 注入；入口仍须返回对象）
const result = notify.publish({
  channel: 'project',
  to: ['project-001'],
  bizCode: 'traffic_capture',
  subCode: 'media_added',
  data: { event_id: eventId }
})
// result: { delivered, skipped, skipReason, failReason }
```

> 字段对应关系：后端 `notify.publish` 的 `bizCode`/`subCode`，到达前端 `ctx.ws.onBizCode` 回调时是 `message.bizCode` / `message.subBizCode`（前端统一驼峰命名）。按 `bizCode` 订阅、按 `subBizCode` 区分具体通知种类。

```ts
// 前端（需 platform:websocket 权限）
await ctx.ws.onBizCode('traffic_capture', message => {
  // 收到通知后重新查询，不要直接把 message.data 当完整记录
  refreshList()
})
```

规则：

- 通知可能被跳过（`skipped=true`）或投递失败（`delivered=false`），业务数据必须**先落库再发通知**，通知失败不能回滚状态。
- 前端收到通知后重新查询权威数据，不要拿通知里的 `data` 当最终记录。
- 通知 `data` 里不要放签名 URL、token 或大段原始数据，放个 ID 就够。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 同一条消息被处理两次 | 至少一次投递的正常行为；用条件更新和唯一键保证副作用幂等 |
| 状态出现回退（已核实又变处理中） | 更新条件没带旧状态，旧的重试覆盖了新状态 |
| 前端刷新依赖通知，通知丢了就"卡住" | 通知只是加速；界面要有定时轮询兜底 |
| 事件脚本缺字段被反复重投 | 契约错误应直接进死信；检查是不是误用了可重试的错误码 |
| 收到通知后界面数据不对 | 把通知数据当记录用了；改为重新调查询接口 |

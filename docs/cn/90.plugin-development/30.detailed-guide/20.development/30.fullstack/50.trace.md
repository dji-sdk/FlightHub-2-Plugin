# 链路标识与诊断日志

一个请求从前端到后端、再到流程实例，中间经过好几个环节。出了问题怎么把它串起来排查？这一页讲平台给你的标识（请求 ID、幂等键、流程 ID）和脚本日志的写法限制，读完你能快速定位"这条请求到底死在哪一步"。

## 平台给你的标识

| 标识 | 从哪来 | 在脚本里怎么读 |
|---|---|---|
| 请求 ID | 调用方 HTTP 头 `X-Request-Id` | `ctx.requestId`（没带头就是空串，平台不代生成） |
| 幂等键 | 调用方 HTTP 头 `Idempotency-Key` | `ctx.idempotencyKey` |
| 事件 ID | 消息的 `event_id` | 事件脚本里同样是 `ctx.idempotencyKey` |
| 流程 ID | `flow.start(流程名, bizId)` 拼出 `流程名-bizId` | 启动响应和流程查询里可见 |
| 步骤幂等键 | `workflowID:stepID` | 流程脚本里读 `run.idempotencyKey` |
| 脚本标识 | 平台登记的脚本键 | `ctx.scriptId` |
| 插件版本 | 清单 `version` | `ctx.pluginVersion` |

要点：`X-Request-Id` 由调用方（前端或网关）生成，平台只透传。前端建议每次用户动作生成一个请求 ID，重试时沿用同一个；幂等语义仍由独立的 `Idempotency-Key` 表达，两者不要混用。

## 接口处理函数里怎么打日志

```ts
// handlers/lane-change/create-event.ts
export function handle (input: RecordInput, ctx: HandlerCtx) {
  log.info('创建变道事件', {
    request_id: ctx.requestId,
    event_key: String(input.event_key || ''),
    idempotency_key: ctx.idempotencyKey,
    script_id: ctx.scriptId
  })
  // ...
  return { request_id: ctx.requestId, event_key: input.event_key }
}
```

平台会自动给每条脚本日志附上 `pluginId / 脚本键 / 幂等键`，插件伪造不了。HTTP 访问日志无论成败都会记录 `pluginId / handler / 结果类别`。

## 从请求 ID 串到流程实例

启动流程时用稳定业务 ID 当 `bizId`，就能从日志一路查到流程：

```ts
const started = flow.start('lane-change-postprocess', `${input.event_id}:${input.video_file_id}`, {
  event_id: input.event_id,
  video_file_id: input.video_file_id,
  video_object_key: input.video_object_key
})
// 流程 ID = lane-change-postprocess-<event_id>:<video_file_id>
// 步骤幂等键 = 流程 ID:<stepId>
```

seed 的键必须和流程 `job.seed` 声明逐字一致，少一个启动就会被拒。

排障时的串联顺序：

```text
X-Request-Id
  → pluginId + handler（定位到哪个接口）
  → event_key / event_id（定位到哪条业务数据）
  → 流程 ID（定位到哪个流程实例）
  → 步骤 ID + 步骤幂等键（定位到哪一步）
  → scriptId + 幂等键（定位到哪版脚本）
```

注意：平台不会自动把 HTTP 请求 ID 带进随后启动的流程。需要业务可查时，用稳定的业务 ID（`event_id` 这类）当关联主轴，不要把请求 ID 塞进所有业务表去模拟链路追踪。

## 脚本日志的限制

```ts
log.info('处理开始', { event_id: eventId, attempt: 1 })
log.warn('媒体链接不可用', { file_id: fileId })
log.error('处理失败', { event_id: eventId, reason: '能力提供方不可用' })
```

| 项目 | 上限 / 行为 |
|---|---|
| 每次脚本调用的日志条数 | 32 条；超出时补一条告警后丢弃 |
| 每条日志的结构化字段 | 8 个；超出按字段名排序截取 |
| 日志消息和字段值 | 512 字节，按 UTF-8 边界截断 |
| 字段名 | 64 字节 |
| 字段类型 | 只接受 string / number / bool / null；对象和数组不记录 |
| 敏感字段 | `token` / `password` / `secret` / `authorization` / `cookie` / `url` 等值替换为 `***` |

两个容易踩的坑：

- 自由文本日志消息不会被自动脱敏，所以不要写 `log.info('请求失败: ' + response.body)`，也不要把配置、token 拼进消息。
- 事件 ID、对象键这类业务标识不会被通用敏感词表打码（排障需要），是否记录按你的数据等级自己判断。

## 日志是尽力而为

没有装配日志器时，`log.*` 什么都不做，也不影响业务。**不要用"日志打没打出来"决定状态迁移**——需要失败就 `throw`，需要降级就在返回值里放显式的标记字段（如 `degraded: true`）并留下净化过的日志。

## 输入、输出与错误的关联建议

- 前端每个用户动作带一个 `X-Request-Id`；重试沿用，方便客服按截图定位。
- 成功响应不会自动回显请求 ID。产品需要时，可以让接口处理函数显式把 `request_id` 放进返回值——但别把它当业务主键。
- 错误响应的 `message` 可能变化。客户端应记录 HTTP 状态、业务 `code`、请求 ID、`pluginId` 和接口名（`handler`），不要记录并依赖 `message` 原文。
- 事件脚本和流程脚本里的 `ctx.requestId` 是空串，用事件 ID / 流程 ID / 步骤幂等键定位。
- 插件热更后，用 `ctx.pluginVersion` 和 `ctx.scriptId` 确认执行的是哪一版脚本；正在跑的流程实例用的可能是旧版定义，排障时两边都要核对。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| `ctx.requestId` 是空串 | 请求没带 `X-Request-Id` 头；平台不会代生成，调用方补上 |
| 日志里 URL 显示 `***` | `url` 是敏感键，值会被打码；确实要记录时换个字段名并自己截断 |
| 第 33 条日志不见了 | 单次调用上限 32 条；合并日志或减少无效输出 |
| 字段值只剩一半 | 单值上限 512 字节；先截断再记录 |
| 排查时对不上脚本版本 | 核对 `ctx.scriptId` / `ctx.pluginVersion` 与当前部署版本是否一致 |

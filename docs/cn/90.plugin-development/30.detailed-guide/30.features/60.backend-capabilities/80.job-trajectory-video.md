# 作业、目标轨迹与视频处理

这一页讲三件配合使用的事：

1. **`flow.start`**：启动声明了 job 轴的流程，本例由 HTTP/事件回调发起。
2. **`objectTrack`**：读视频的目标轨迹，本例安排在流程脚本里。
3. **`video`**：做视频探测、抽帧、剪片，本例安排在流程脚本里。

HTTP、事件和流程脚本三路共用按有效 `allowlist` 注入的方法。重耗时的视频处理建议放在流程作业里，这是超时与重试设计建议，不是路线硬隔离；**注入不代表部署的能力提供方可用**，仍需处理调用点的错误或 `skipped`。飞行/裸设备函数不注入脚本。

## 第 1 步：声明 `job` 触发的作业流程

目标流程必须声明 `job` 触发轴，`seed` 列出调用方必须传的字段名：

`my-plugin/workflows/lane-change-postprocess.json`：

```json
{
  "name": "lane-change-postprocess",
  "trigger": {
    "job": { "seed": ["event_id", "video_file_id", "video_object_key"] }
  },
  "steps": [{
    "id": "postprocess",
    "action": "run_script",
    "timeoutSec": 300,
    "inputs": {
      "script": { "const": "lane-change-postprocess" },
      "event_id": { "from": "trigger.event_id" },
      "video_file_id": { "from": "trigger.video_file_id" },
      "video_object_key": { "from": "trigger.video_object_key" }
    }
  }]
}
```

## 第 2 步：在回调里启动作业

权限 `flow:start`，三路均按有效 `allowlist` 注入；本例由 HTTP/事件回调启动作业：

```ts
// handlers/... 或 events/...
const result = flow.start("lane-change-postprocess", event.id, {
  event_id: event.id,
  video_file_id: event.video_file_id,
  video_object_key: event.video_object_key
})
// { already: false } 新启动；{ already: true } 同一作业已存在——两者都不是错误
```

本页第 1、2 步是三键片段示例：`event_id`、`video_file_id`、`video_object_key` 必须同时声明和传递。[事件、通知与状态](../../20.development/30.fullstack/30.events-and-state.md)及[交通抓拍](../../50.examples/50.traffic-capture.md)的两键补偿例子是另一份简化片段示例，不是与本页直接拼装的完整后处理流程。

规则：

| 规则 | 说明 |
| --- | --- |
| 幂等 | 同一 `(flowName, bizId)` 靠流程实例 ID 去重；`already=true` 按正常结果处理 |
| seed 对账 | 传入的键必须与 `trigger.job.seed` **逐字一致**，缺键多键都报错 |
| 必填 | `flowName` 和 `bizId` 都不能为空 |
| 重跑 | 没有 `retry` 方法；要重跑就生成新的 `bizId` |
| 查进度 | 没有 JS 查询方法；用平台的状态查询端点按 `(flowName, bizId)` 查 |

调用只是函数内片段；HTTP 接口处理函数、事件入口和流程脚本**必须返回对象**，无业务输出通常返回 `{}`。`flow.start` 返回 `{already}`，其他方法按各自签名处理，不能统一读 `.ok/.data`。事件入口顶层失败信封会分类消息处置；HTTP 接口处理函数和流程脚本**不自动提升返回的失败信封**，例如 `store` 操作失败需要让调用失败时应显式 `throw result.error`，见[能力目录](../../70.api-reference/20.backend/80.host-capability-catalog.md#返回与错误)。

## 第 3 步：流程脚本里处理轨迹和视频

权限 `track:read` / `video:process`，写在对应脚本的 `scripts[].allowlist` 里。

这是本例的分工，不是权限按路线分层。流程脚本也能获得 `flow.start`，递归启动和流程步骤重试的副作用仍需评审，不能依赖路线隔离防住。

### objectTrack：目标轨迹

```ts
// 看视频某个时间窗内有没有轨迹数据
const timeline = objectTrack.inspect(
  { fileId: "...", objectKey: "..." },
  { rawStartMs: 1780000000000, rawEndMs: 1780000008000 }   // 录制起止墙钟毫秒
)
// -> { firstFrameNo, lastFrameNo, fps, durationMs, startWallClockMs }

// 取某目标在某时间段的轨迹采样
const track = objectTrack.getTrack({
  fileId: "...", objectKey: "...", objectId: "...",
  fromMs: 0, toMs: 5000, fps: 30
})
// -> { samples: [{ frameNo, offsetMs, x, y, w, h }], durationMs }
```

要点：

- `samples=[]` 是合法结果（目标在窗口内没出现）；配套轨迹文件不存在或解析不了才抛错。
- `x/y/w/h` 是 `[0,1]` 归一化坐标；帧号已按配套轨迹文件的最小帧归零。
- `inspect`/`getTrack` 是只读操作，可以安全重试。
- `startWallClockMs` 用于把业务时间（如抓拍时刻）换算成视频内时间。

### video：视频处理

```ts
// 探测视频元信息
const info = video.probe({ fileId: "...", objectKey: "..." })
// -> { durationMs, width, height, fps, keyframeIntervalMs }

// 按时刻抽帧（返回每帧的新文件 ID）
const frames = video.extractFrames(
  { fileId: "...", objectKey: "..." },
  [1000, 2000, 3000],
  { projectId: "...", dockSn: "...", flightId: "..." }
)
// -> [{ atMs, fileId, skipped, skipReason }]

// 剪一个片段（生成新文件）
const clip = video.createClip(
  { fileId: "...", objectKey: "..." },
  500, 8000,
  { projectId: "...", dockSn: "...", flightId: "..." }
)
// -> { fileId, actualStartMs, actualEndMs, durationMs, skipped, skipReason }
```

要点：

- 抽帧时单个越界时刻返回 `skipped=true`（带 `out_of_range` 原因），其他帧照常；空时刻列表、`endMs <= startMs` 是契约错误。
- 剪片按关键帧对齐，**实际起止点可能比请求值提前**——必须保存返回的 `actualStartMs/actualEndMs`，不要用请求值代替。
- `extractFrames`/`createClip` 会生成新文件并注册到媒体系统，**本身不保证重试不产生重复文件**：业务上要用 `store` 的唯一键 + 条件 update 吸收重放。
- 视频的 `objectKey` 参数由平台透传，不要自己拼接任意对象键；媒体签名 URL 不能当视频引用用（会过期且带凭据）。

### 组合示例：从抓拍时刻剪证据片段

```ts
// adapters/postprocess.ts（流程脚本）
const ref = { fileId: input.video_file_id, objectKey: input.video_object_key }

const info = video.probe(ref)
if (!info.fps) throw { code: "VIDEO_FPS_UNKNOWN", message: "无法取得视频帧率" }

const rawStartMs = Number(input.video_start_ms)
if (!Number.isFinite(rawStartMs) || rawStartMs <= 0) throw { code: "VIDEO_TIMELINE_UNKNOWN", message: "录制起点无效" }
if (info.durationMs <= 0) throw { code: "VIDEO_TIMELINE_UNKNOWN", message: "无法取得视频时长" }

const timeline = objectTrack.inspect(ref, {
  rawStartMs,   // 录制起点，墙钟毫秒
  rawEndMs: rawStartMs + info.durationMs
})
if (!timeline.startWallClockMs) throw { code: "VIDEO_TIMELINE_UNKNOWN", message: "无法建立视频时间基线" }

const center = input.crossed_at_ms - timeline.startWallClockMs   // 业务时间 -> 视频内时间
const track = objectTrack.getTrack({
  fileId: ref.fileId, objectKey: ref.objectKey, objectId: input.object_id,
  fromMs: Math.max(0, center - 10000), toMs: center + 10000, fps: info.fps
})

const owner = { projectId: input.project_id, dockSn: input.dock_sn, flightId: input.flight_id }
const frames = video.extractFrames(ref, [center - 1000, center, center + 1000], owner)
const clip = video.createClip(ref, Math.max(0, center - 7000), center + 7000, owner)
```

两处时间别混：`rawStartMs` 与 `rawStartMs + info.durationMs` 是录制窗口的墙钟时间，`center` 是业务时刻减录制起点，得到"视频内第几毫秒"。后面抽帧和剪片用的都是这个视频内时间。

## 部署依赖

轨迹和视频能力由部署方接通；`typeof` 检查只能确认方法已注入，不能证明能力提供方可用。测试前请部署方确认对象存储、视频处理和媒体登记已就绪。缺什么会表现为不同的错误：

| 缺什么 | 表现 |
| --- | --- |
| 对象存储未接入 | 轨迹和视频方法即使已注入，调用仍抛错 |
| 视频处理提供方未就绪 | 视频方法调用抛错；对象存储等前置条件已就绪时，轨迹仍可用 |
| 媒体登记服务接入 | `probe` 可用；抽帧和剪片在上传阶段失败 |

生产验收要用真实的配套轨迹文件和录制文件验证帧号、时间基线、抽帧精度和剪片偏移。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| `flow is not defined` | 检查有效 `allowlist` 的 `flow:start`，以及流程脚本是否覆盖了包级申报；三路都可注入 |
| `objectTrack is not defined` | 检查有效 `allowlist` 的 `track:read`；方法存在但报未装配时另查部署的能力提供方 |
| `video is not defined` | 检查有效 allowlist 的 `video:process`；重活放作业是工程建议，不是注入限制 |
| `flow.start` 报 seed 不匹配 | 与 `trigger.job.seed` 逐字核对键名 |
| 剪片起止点和请求不一致 | 关键帧对齐导致；用返回的 `actualStartMs/actualEndMs` |
| 重试后出现重复抽帧文件 | 抽帧/剪片非幂等；用 store 唯一键做业务去重 |

job 之外的其他触发轴见[触发方式](../../20.development/20.backend/70.triggers.md)；流程脚本声明见 [plugin.json 契约](../../20.development/20.backend/10.plugin-json.md)。

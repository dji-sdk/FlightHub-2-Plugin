# 后端能力总览

后端插件能调用的平台功能（存数据、读配置、出网、发通知……）不是 `ctx` 上的方法，而是平台按 `allowlist` 注入的**全局对象**。这一页给出完整的能力表：有哪些全局对象、每个对象有哪些方法、需要申报什么权限、在哪些代码路线里可用。

## 三条代码路线

一个后端插件里有三种**业务执行路线**（HTTP、事件、流程脚本，都是 TypeScript 源文件，构建后装载执行）。另有一个只读判定入口 `evaluators`，它由受审步 `evaluate` 调用，注入面恒空，只保留 `log`，不参与下面的能力表。

三条业务路线共用按有效 `allowlist` 注入的方法，区别是调用上下文、超时和重试边界：

| 路线 | 代码位置 | 权限声明在哪 |
| --- | --- | --- |
| HTTP 接口处理函数 | `handlers/**/*.ts` | 插件清单顶层 `allowlist` |
| 事件回调 | `events/` 下的订阅回调 | 插件清单顶层 `allowlist` |
| 流程脚本 | `adapters/` 下的脚本，由流程的 `run_script` 步执行 | 非空 `scripts[].allowlist` 覆盖包级；为空或未写则回落包级 |

下表中"三路"指以上三条路线都可用。

## 能力总表

能力名全集共 19 个（log 无需申报）。申报了平台授不出的能力名，插件进程起不来。

先按你要做的事找对象，再看方法签名：

- 读写业务数据：`store`、`cache`
- 调外部系统：`connector`、`platform.getConfig`
- 处理媒体：`media`、`objectTrack`、`video`
- 编排或通知：`flow`、`notify`
- 飞行任务：流程受控步（如 `dispatch_mission`）
- 航线、截图：`wayline`、`screenshot`

| 全局对象 | 方法 | 需要的权限 | 可用路线 |
| --- | --- | --- | --- |
| `log` | `info / warn / error` | 不需要申报 | 三路 |
| `platform` | `getConfig()` 读连接配置、`insertEvent(ev)` 写事件、`resolveSegment(lat,lng)` 解析路段 | `config:get`、`event:write`、`geo.segment:read` | 三路 |
| `connector` | `invoke(id, payload)` 调平台连接器、`fetch(req)` 受管出网 | `integration:write` / `integration.gis:read`（invoke）、`egress:fetch`（fetch） | 三路 |
| `store` | `query / count / insert / createIfAbsent / update / delete` | `data:read`（前两个）、`data:write`（后四个） | 三路 |
| `cache` | `get / set / del / expire / incr / hset / zadd / …` 等缓存操作 | `cache:read` / `cache:write` | 三路 |
| `media` | `get`（读，接真）、`list`（读，当前不可用）；`attach`（写，空壳）、`ensureFolder / move / rename`（写，接真需配置与 workspace） | `media:read` / `media:write` | 三路 |
| `flow` | `start(flowName, bizId, seed)` 启动本插件的 job 流程 | `flow:start` | 三路按 allowlist |
| `notify` | `publish({channel,to,bizCode,subCode,data})` 给前端发通知 | `notify:publish` | 三路按 allowlist |
| `wayline` | `generate(...)` 生成示教航线 | `wayline:generate` | 三路按 allowlist |
| `screenshot` | `signUrl(key)` 预签名、`issueUpload(...)` 签发上传凭据 | `screenshot:signurl` / `screenshot:issueupload` | 三路按 allowlist |
| `objectTrack` | `inspect / getTrack` 读目标轨迹 | `track:read` | 三路按 allowlist |
| `video` | `probe / extractFrames / createClip` 视频处理 | `video:process` | 三路按 allowlist |

工程建议与部署边界：

- 重耗时的视频处理建议放在流程作业里，这是超时与重试设计建议，不是路线硬隔离。
- 流程脚本也可获得 `flow.start`；调用须评审稳定业务键、seed、递归和重试副作用，不能靠路线隔离兜底。
- **注入不代表部署的能力提供方可用**；方法可能在调用点报未装配或返回 `skipped`，具体按方法签名处理。

## 怎么用

第 1 步，在源清单 `fh2-plugin.json` 的 `allowlist` 里申报权限：

```json
{ "allowlist": ["data:read", "data:write", "media:read"] }
```

第 2 步，代码里直接用全局对象，不需要任何获取动作：

```ts
// handlers/report/list.ts
export function list (input: RecordInput, _ctx: HandlerCtx) {
  const page = store.query('task', { status: { eq: 'new' } }, { limit: 20 })
  const m = media.get(input.file_id)
  log.info('done', { total: page.data.total })   // log 不需要申报
  return { total: page.data.total }
}
```

⚠️ **没申报的对象根本不存在**——不是报"权限拒绝"，而是 `TypeError: xxx is not defined`。看到 TypeError 先检查清单的 allowlist。

## ctx：只有调用事实，没有能力

`handle(input, ctx)` 的第二个参数只装这次调用的事实（平台时间、幂等键、请求 ID 等），上面没有任何能力方法。详见 [ctx 与能力注入](../../20.development/20.backend/40.context-and-allowlist.md)。

## 返回形态

- `store` 方法返回 `{ok:true,data}` 或 `{ok:false,error:{code,message}}`，操作失败要检查 `ok`；下面的 `must` 只适用于这种信封结果。
- `cache` 请逐方法查工程生成的 `types/`；其他能力按[能力目录](../../70.api-reference/20.backend/80.host-capability-catalog.md#返回与错误)的具体签名处理，不统一套用信封或 `try/catch`。例如 `flow.start` 返回 `{already}`，`connector.invoke` 返回 boolean，`notify.publish` 返回投递状态对象。

```ts
function must<T>(result: { ok: true, data: T } | { ok: false, error: { code: string, message: string } }): T {
  if (!result.ok) throw { code: result.error.code, message: result.error.message }
  return result.data
}
const page = must(store.query('task', {}))
```

HTTP 接口处理函数、事件入口和流程脚本**必须返回对象**，通常为 `{}`。事件入口顶层返回 `{ok:false,error:{code,message}}` 会按 `error.code` 分类消息处置；HTTP 接口处理函数和流程脚本**不自动提升返回的失败信封**，操作失败需要让调用失败时必须显式 `throw result.error`。

## 硬隔离：飞行控制不面向脚本

下发任务、返航这类高危动作**从不注入脚本**——脚本里没有任何飞行函数。飞行操作只能通过流程 JSON 里的平台受控步（如 `dispatch_mission`）完成，平台在这些步骤上做校验。详见[飞行任务与违停巡逻](./40.flight-task-patrol.md)。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 调用报 `TypeError: store is not defined` | 检查有效 `allowlist` 是否申报 `data:read/data:write`，以及流程脚本是否覆盖了包级列表 |
| 申报了能力名，进程起不来 | 申报了平台授不出的名字（如 `lease:*`），改成 19 个合法能力名 |
| 在流程脚本里用 `flow.start` 报未定义 | 检查有效 `allowlist` 的 `flow:start`；三路都按申报注入，报未装配则另查部署的能力提供方 |
| 在 HTTP 回调里用 `objectTrack` 报未定义 | 检查 `track:read`；重活建议交给 `run_script` 作业，但这不是注入限制 |

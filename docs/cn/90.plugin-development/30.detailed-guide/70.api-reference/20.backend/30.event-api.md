# 后端事件消费参考

事件消费让插件在「某类消息产生」时自动执行脚本，比如视频转码完成后做后处理。消息由平台投递（至少一次），插件只写消费脚本并在源清单 `events[]` 里声明。你写 TypeScript 源文件，构建后由运行时装载执行。

## 清单声明

```json
{
  "events": [
    {
      "type": "media.video_created",
      "match": {"sub_file_type": "0"},
      "consumer": [{"handler": "events/on-video.ts", "entry": "onVideoCreated"}]
    }
  ]
}
```

| 字段 | 必填 | 规则 |
| --- | :---: | --- |
| `type` | ✅ | 包内唯一；只能选订平台指定的类型（当前为 `media.photo_created`、`media.video_created`），不能自造。模板自带的 `example.created` 仅用于本地模拟联调 |
| `match` |  | 消息体顶层字段等值筛选（AND），值按字符串比较；不写 = 全收 |
| `consumer` | ✅ | 非空数组；后端运行时对命中的消费方并发执行、各自独立重试；全部结束后按最坏结果聚合消息处置 |
| `consumer[].handler` | ✅ | 包内相对 TS 路径，文件必须存在 |
| `consumer[].entry` |  | 入口导出函数名，缺省 `handle` |

同一 `type` 可以被多个插件订阅，消息会扇出到每个订阅者。

`consumer` 数组不保证执行先后。有业务依赖的逻辑应放在同一个消费函数内调用，或使用显式流程编排，不能依赖另一个消费方先写完数据。

## 消费脚本

> `fh2-plugin-sdk/backend` 表示插件 SDK 的后端类型入口；实际导入路径保留生成工程的配置，不按示意名安装依赖。

```ts
// events/example-created.ts（模板自带）
import { ingestEvent } from '../shared/records'
import type { RecordInput } from '../shared/records'
import type { EventCtx } from 'fh2-plugin-sdk/backend'

export function onExampleCreated (event: RecordInput, ctx: EventCtx) {
  // 入参是消息信封 { id, type, data }，业务字段住在 data 里
  const nowMs = Date.parse(ctx.now)
  return ingestEvent(event, Number.isFinite(nowMs) ? nowMs : 0)
}
```

- 签名 `entry(event, ctx)`；消息信封完整传入，`ctx` 见[脚本上下文](./40.context-api.md)（事件侧的 `requestId`/`idempotencyKey` 由消息消费填充）。
- **入口必须返回对象**，通常为 `{}`；若入口直接返回辅助函数的结果，该结果也必须是对象。执行到函数末尾但未返回、`return undefined` 或裸 `return` 会被后端运行时当作可重试错误，耗尽后丢弃（`Discard`）。
- 普通业务输出不会交给其他消费方；事件入口顶层返回 `{ok:false,error:{code,message}}` 时，后端运行时按 `error.code` 分类处置。嵌套失败信封或忽略失败后返回 `{}` 不会自动变成错误。
- **HTTP 接口处理函数和流程脚本不自动提升返回的失败信封**。若 `store` 操作失败应让调用失败，必须显式 `throw result.error`，不能套用事件入口的信封分类规则。
- **"这条消息不是给我的"绝不抛**：你的契约错会把消息打进死信，拖累同队列其他消费方——安静返回空对象。
- HTTP、事件和流程脚本三路均按有效 `allowlist` 注入方法，包括轨迹、视频和内部流程启动。重活建议用 `flow.start()` 交给作业流程，这是工程建议，不是路线硬隔离；注入不代表部署的能力提供方可用，见[能力目录](./80.host-capability-catalog.md)。飞行/裸设备函数不注入脚本。

## 投递语义（至少一次）

| 情况 | 平台动作 |
| --- | --- |
| 消息 JSON 解析失败 | 确认并告警（重投也不会好） |
| 该类型没有任何插件订阅 | 确认并告警 |
| 有订阅但 `match` 不命中 | 确认（正常过滤） |
| 所有命中消费方的处置均为确认（`Ack`） | 确认，包含正常返回和业务结果 |
| 业务错（`NOT_FOUND`/`DUPLICATE`/`CONFLICT`） | 确认，不重投 |
| 契约错（`INVALID_ARGUMENT` 等） | 丢弃/进死信，不重投 |
| 其他错误或非对象返回 | 各自按部署的 `MaxAttempts` 有界重试，耗尽后丢弃（`Discard`） |
| 可重试错误处理/退避期间因关停取消 | 重新入队（`Requeue`） |

错误分类同时适用于抛出的错误和事件入口顶层的失败信封。后端运行时等全部消费方结束后，按 **`Requeue > Discard > Ack`**（重新入队 > 丢弃 > 确认）聚合一条消息的处置；一个消费方失败不会阻止其他消费方执行。丢弃（`Discard`）在队列配置了死信交换机时进入死信队列。

⚠️ 至少一次投递意味着**脚本可能被重复执行**（进程重启后重试计数也会重置）。去重必须用 `store.createIfAbsent` + 唯一键，不要「先 query 再 insert」。

本地联调用模拟投递：`pnpm run dev` 后 `POST /plugin-api/mock/backend/event`，工程 `backend/<id>/README.md` 有完整演示。

本地模拟器不覆盖消息队列的并发、独立重试和确认/死信语义；这些行为需在已部署的测试环境验证。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 同一条消息处理了两次 | 至少一次投递的正常行为；补幂等去重 |
| 消息一直没到 | `type` 拼错、`match` 条件不命中，或现场没配置该事件源 |
| 消息进了死信 | 抛了契约错；检查参数处理逻辑，缺字段应视为数据问题而不是抛 `INVALID_ARGUMENT` 后等待重试 |
| 想在事件里直接处理视频 | 按 `track:read` / `video:process` 注入；重耗时处理建议交给作业流程，并另行确认部署的能力提供方可用 |

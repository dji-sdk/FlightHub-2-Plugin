# 后端运行时与流程调试

后端插件先用**工具链本地 HTTP 模拟器**（`pnpm run dev`）调试 HTTP 接口、事件脚本与内存数据，再到已部署测试环境验证后端运行时、流程和队列行为。Toolchain `1.0.0` 当前模拟器使用数字错误信封，但 HTTP 状态、消息包装和真实存储运行条件仍与部署环境存在差异，不是真实网关。

> 用真实司空环境验证前端产物的行为，见[真实环境预览](./10.local-development.md)——它只覆盖前端，后端用的是目标环境已安装的版本。

## 本地接口调试

先确认生成工程的依赖已安装、后端目录存在，且未使用 `--frontend-only`。在能力工程工作区根执行 `pnpm run dev` 会构建后端并启动本地调试页面与本地 HTTP 模拟器。想**只用 curl 调试后端**（不启动前端界面），可将 `--root` 指向实际后端插件目录：

```bash
# 从工作区根执行，路径以生成工程结构为准
pnpm exec fh2-plugin dev --root "<实际后端插件目录>"
```

`build` 仅生成产物，`pack` 构建并组装交付包，两者都不启动网关或服务。只有 `dev` 在含后端且非 `--frontend-only` 的条件下启动本地 HTTP 模拟器；它不执行流程。

`<实际后端插件目录>` 替换为含后端源清单的目录；例如生成工作区中的 `<能力工程目录>/backend/<后端插件ID>`，不要把工作区根与能力工程根混用。

接口入口为 `POST /plugin-api/plugin/invoke`。使用工程后端 README 的请求结构，但不要硬编码示例凭据：先按开发环境接入说明取得与本机模拟器匹配的有效插件 Token，设置 `FH2_LOCAL_PLUGIN_TOKEN`，并按实际端口设置 `FH2_LOCAL_ORIGIN`。未取得凭据时使用本地调试页面，或联系技术支持；不要从实现常量取值，也不要去掉鉴权头。下面的请求只适用于你自己启动的回环模拟器，不能发往真实网关：

```bash
# 前置条件：上述环境变量已设置，后端插件和 example.create 已装载
curl -sS -X POST "${FH2_LOCAL_ORIGIN:?}/plugin-api/plugin/invoke" \
  -H "Origin: ${FH2_LOCAL_ORIGIN:?}" \
  -H "x-plugin-token: ${FH2_LOCAL_PLUGIN_TOKEN:?}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: local-create-001' \
  --data '{"pluginId":"<后端插件ID>","handler":"example.create","input":{"record_key":"local-001","title":"调试记录"}}'
```

将 `<后端插件ID>` 替换为实际 `pluginId`；重复创建时复用同一个业务键和幂等键。真实环境使用部署方提供的授权凭据，不使用本地调试 Token。

## 三种入口各自怎么测

| 入口 | 怎么触发 | 怎么确认 |
| --- | --- | --- |
| HTTP 接口处理函数 | 使用上面的 `invoke` 请求（带本机调试 Token，写操作带幂等键） | 成功看 `code: 0` 和 `data`；失败看数字 `code`、HTTP 状态与文案，经前端调用时核对 `detail.gatewayCode` |
| 事件处理函数 | `POST /plugin-api/mock/backend/event`，请求体用 `mock/events/` 里的测试数据 | 响应里看处理结果；`GET /plugin-api/mock/backend/state` 看数据落库 |
| 流程 | 本地 `dev` **不执行**流程；`validate` / `build` 检查流程 JSON、脚本入口和输入输出接线 | 启动、信号等待、步骤重试在已部署测试环境验证，见[流程编排](../20.development/20.backend/60.workflow.md) |

## 模拟数据状态的三个辅助端点

| 端点 | 用途 |
| --- | --- |
| `GET /plugin-api/mock/backend/state` | 看内存库的原始行（平台四列 `id/tenant_id/created_at/updated_at` 是注入的） |
| `POST /plugin-api/mock/backend/reset` | 清除本轮写入并恢复初始测试数据，不保证空表 |
| `POST /plugin-api/mock/backend/event` | 投递一条消息给事件消费方 |

这些端点仅用于本机模拟数据，随当前 `dev` 的后端加载状态开放。它们当前不检查插件令牌，但本地调试页面同源门禁要求请求携带与监听地址一致的 `Origin`；不要据此认为真实接口可以跳过鉴权，也不要把辅助端点暴露给外网。真正的 `/plugin-api/plugin/invoke` 仍需有效插件令牌。

内存数据仅属于当前 dev 进程。保持该进程及后端数据结构不变时，刷新浏览器后仍能读回；重置会清除本轮写入并恢复初始数据，重启 dev 或重建导致实体结构变化也会丢失本轮数据。这不是持久化存储验证。

## 本地模拟器与真实环境的差异

本地模拟器可检查接口寻址、插件输入校验、基本存储读写和界面/HTTP 协作。它不等于：

- 生产数据库（本地是内存表；生产建表要执行 `schema.sql`）
- 消息队列的投递语义（本地是手动调用；部署环境是至少一次投递，并有并发、重试与消息处置）
- 流程引擎（本地不执行流程）

所以本地跑通后，涉及流程、事件重投或真实存储的行为要在目标环境复验。

## 已知限制

| 项目 | 本地模拟器的限制 | 验证方式 |
| --- | --- | --- |
| 错误信封与 HTTP | 当前后端错误映射为数字 `40006` / `20001` / `50301`，但保留本地 HTTP 状态；缺幂等键为 400 / `40006`，未知接口为 404 / `40006`，`NOT_FOUND` 为 404 / `20001`，`CONFLICT` 为 409 / `20001`；未分类 `BRIDGE_FAILED` 为 400 / `50301` | 本地可验证数字信封与前端 `PLUGIN_GATEWAY_ERROR` 的 `detail.gatewayCode`；目标网关和直接后端服务的 HTTP / 鉴权行为另验，不能由 HTTP 400 推断错误分类 |
| invoke 顶层校验 | 多余顶层字段可能被接受，不能证明正式 `40001` 拒绝行为 | 请求仍只传 `pluginId` / `handler` / `input`，在已部署环境测试多余字段 |
| 媒体消息形状 | 本地消息会包装为含 `data` 的信封，不能直接证明读取真实消息顶层 `file_id` 的消费链路 | 模板 `example.created` 仅用于本地；真实媒体链路按目标消息定义验证，不增加双形状兜底 |
| 排序与分页 | 本地支持 `field/dir` 和 keyed 对象式 `orderBy`，以及 limit/offset；脚本返回公开 `createdAt/updatedAt`，原始快照仍是物理列。它不模拟数据库事务、SQL 执行或部署数据规模 | 保留正式查询形状；本地检查排序、分页和公开字段，真实数据库行为与历史规模在部署环境复验 |
| 列表演示 | [最小全栈示例](../50.examples/30.minimal-fullstack-plugin.md)只查询 20 行；按创建时间倒序，只显示最新 20 行，不能查看更早历史 | 按示例的空数据前提测试创建与状态推进；不将本地列表当作无限历史验收 |
| 消费与流程 | 本地模拟器不用于证明消费方并发、独立重试、消息确认/死信处置或流程执行 | 在已部署测试环境验证，消息重放与依赖恢复由部署方协助 |


## 流程与队列验证

流程 JSON 的字段校验在 `pnpm run validate` 中执行；`pnpm run build` 生成资产，但不会启动流程服务。已有测试环境的验证步骤：

1. 请部署方确认插件版本和流程已装载、`schema.sql` 已执行、能力提供方和队列已就绪，并取得环境入口与授权方式。
2. 在插件已有测试中验证每步业务逻辑，再使用隔离业务 ID 触发声明的流程；不要为调试新增公开接口暴露流程脚本。
3. 查询流程当前状态和 `awaitingSignal`，按声明投递人工信号；检查重复触发同一业务 ID、步骤失败与收尾分支。
4. 与部署方协作投递真实形状的测试事件，验证并发消费、独立重试和最终处置。耗尽重试后的恢复需要明确的人工重放或对账方案，不承诺自动死信恢复。
5. 失败时保留流程 ID、步骤 ID、插件版本、业务码和时间范围，联系技术支持或部署方；错误含义见[错误码](../80.error-codes.md)。

## 排错速查

| 现象 | 处理 |
| --- | --- |
| curl HTTP 404 / `code: 40006`，文案含 `PLUGIN_NOT_FOUND` 或 `HANDLER_NOT_FOUND` | `pluginId` 写错（要用后端插件的 ID）、接口名和文件路径/导出名对不上、或启动时用了 `--frontend-only` |
| HTTP 503 / `code: 50301`，文案含 `BACKEND_DIST_MISSING` | 后端构建失败；先修 `pnpm run build` 的第一条报错再启动 dev |
| 事件投了没反应 | `type` 拼错、`match` 不命中，或测试数据的字段形状和消息定义不一致 |
| 改了 TS 没生效 | dev 的热更基于构建；确认终端没有构建报错，必要时重启 dev |

## 验证清单

- [ ] curl 调用返回 `code: 0`，`mock/backend/state` 能看到数据。
- [ ] 重复投递同一事件（换消息 id、同一业务键）不产生重复数据——幂等是入场券。
- [ ] 本地参数错返回数字 `40006`；实际业务结果与系统错分别核对 `20001` / `50301`，保留本地 HTTP 差异，不把 HTTP 400 一律当契约错。
- [ ] 前端非零信封抛 `PLUGIN_GATEWAY_ERROR`，数字业务码在 `detail.gatewayCode`；部署服务与目标网关行为另验。
- [ ] `mock/fixtures/` 与 `schema.sql` 派生的实体声明一致（测试数据里的实体名和字段要能对上）。
- [ ] 真实媒体消息形状、查询排序与分页、流程及队列行为在测试环境另验，没有用模拟结果替代。

# 06 构建交付与打包（Build & Pack）

何时读取：Step 4，构建产物、生成上传包、交付核对与汇报。

前置条件：Step 3 验证序列全部通过。

## 构建

- `fh2-plugin build` 把所选范围构建到 `dist/`。范围与方案中的受影响插件一致，不扩大。
- `dist/` 归构建工具（tsup/Rsbuild）所有。禁止手工创建，或往 `dist/` 里拷产物。
- MCP 场景下 `build` 返回 `taskId`，按 05 的任务模型轮询终态。

## 执行目录与制品判别（pack 前必做）

pack 产出什么，由执行目录的根标记决定。下表是路由示意，具体以契约机器事实和本次实际输出为准。

| 根标记 | 制品 | 可上传 |
| --- | --- | --- |
| `packages.json`（能力工程根） | 打包全部能力，单个上传 zip | 可上传 |
| `capabilities.json`（能力根） | 平台可上传 zip（含 `packages.json`） | 可上传 |
| `fh2-plugin.json`（单插件根） | 独立插件交付物 + zip | 不可上传 |

- 结论：Skill 只在能力工程根或能力根执行 pack；单插件根不执行 pack。
- 单插件根确实能生成独立插件交付物和 zip，帮助文本里也这么写。但那不是可上传的能力交付包，
  Skill 不走这条路。
- 存量或用户自建的单插件工程需要可上传制品时，走迁移路径。CLI 没有"单插件转上传包"的命令，
  迁移由 Skill 引导完成，共五步：

1. 经确认用 `create --template capability-fullstack` 新建能力工程，目录和 ID 按方案确定。
2. 按 02 的加插件规则，把插件目录移植成能力工程里的插件。
3. 在工程根执行 `install`。
4. 依次执行 `generate`、`validate`、`build`。
5. 在**能力工程根**执行 `pack`。

## 打包（pack）

pack 会生成交付制品，还可能触发重建。执行前单独向用户说明并确认，判别做完再执行：

```sh
fh2-plugin pack
```

- 在能力工程根产出包含全部能力的单个上传包；在能力根产出该能力的上传包。兼容旧的 `plugins/*` 聚合。
- **生态包不带签名是平台设计**：官方发布包的 Ed25519 签名属独立发布流程，生态/第三方包不带签名是常态。
  汇报中不把"未签名"当缺陷、边界或告警项申报。pack 不自动签名、上传或部署。
- MCP 的 `pack` 同样按任务模型轮询；`noBuild` 参数按需跳过重建（只能在能力根用）。

## 上传包核对

pack 的结构校验由所选本地 Toolchain 承担。命令成功只证明它实际检查过的那部分结构；失败按诊断自纠（见 05）。
字段与布局规则按同包开发运行时数据或实际产物查证，不能用授权源码安装或 manifest 探测来证明打包成功。
独立前端/后端模板不一定有 `pack` script，执行位置按 02 与实际 README 核对。人工核对只做三件事：

1. 产物存在：路径、版本、范围与方案一致。
2. `package.json` 没有 `workspace:` 依赖协议残留。
3. Manifest 声明的权限与实现实际所需一致，不多不少。

SDK/Toolchain 的工程依赖与覆盖只引用确认过的授权源码 `file:` 来源，不写完整 Contract 依赖或私有 scope。
保留本次源码身份、制品版本与数据来源/摘要；不把来源摘要当公开字节摘要或发布许可。

上传包按生态交付规则走：上传与平台安装是后续独立步骤（经插件管理完成）。pack 成功只证明本次构建与结构校验通过，
未执行的上传/安装如实标注未验证。签名私钥、真实环境和平台安装各需相应角色及单独同意；不得读取、保存或代输凭据。
报告不保存会话 URL、Token、Cookie、私钥、客户数据或环境全集。

## 交付汇报

使用以下结构汇报（未执行的校验不得描述为通过）：

```markdown
# 交付汇报
## 1. 交付物（路径、版本、范围）
## 2. 行为与契约变更
## 3. 已执行验证（generate/types/validate/test/typecheck/build/pack 及结果）
## 4. 未执行项与原因
## 5. 已知限制与遗留假设
## 6. 待确认的后续动作（dev/preview/安装到环境等）
```

## 约束自查

交付汇报末尾附约束自查段，只列本次实际命中的约束 ID：已满足标 ✅，需用户注意标 ⚠️。
约束 ID 是各纪律表既有序号的一对一引用。句子是权威定义，ID 只是索引；没命中的不列，不逐条抄全部规则：

```markdown
> **约束自查**
> - ✅ R2 契约查证：所有扩展点位均来自生成类型声明
> - ✅ FV6 资源清理：监听器已注册资源跟踪
> - ⚠️ FV1 存储边界：使用了 ctx.storage，请确认已声明 platform:storage 权限
```

可用 ID 来源：红线 R1-R4（SKILL.md）、View 禁令 FV1-FV8（03）、MCP 任务纪律 MCP1-MCP5（05）。
前端任务至少覆盖命中的禁令条目与红线；后端或全栈任务另加其纪律表的命中项。

## 出口条件

- [ ] pack 产物存在，人工核对 1-3 全部通过。
- [ ] 交付汇报已输出，路径与结果真实；命中约束的自查段已附。
- [ ] 临时进程与会话已清理，脱敏报告里没有凭据或客户数据。
- [ ] 制品类型与上传边界已如实说明，含生态包不带签名的平台设计。
- [ ] 未执行的验证没有写成通过，没有越过角色和操作授权。

## 反模式

- 没确认就 pack，或把 pack 当普通构建随手跑。
- 在单插件根执行 pack；用户需要可上传制品时不做迁移引导。
- 手工修补 `dist/` 内容让核对通过。
- 交付汇报里写"测试全部通过"，实际没跑。
- 把"未签名"当缺陷或告警申报（生态包不带签名是平台设计）。
- 忽略外层 `plugin.json` 与嵌入 manifest 的字段重复问题。

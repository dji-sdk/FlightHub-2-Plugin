# 01 需求拆解与方案规划（Planning Spec）

何时读取：Step 1，用户描述了插件需求（新建、扩展、改造）。

两段式：

- **Step 1A 需求澄清**：不依赖任何安装。按决策树分轮交互式提问，把用户目标、场景、偏好问清。
- **Step 1B 方案设计（先查契约）**：需要实际读取所选 Toolchain 的开发运行时数据。

Step 1B 的入口判据是 `execution.status === 'ready'` 且 `contract.path` 非空，判据边界详见 00。
未就绪时按 00 经用户确认后补齐授权源码；
用户拒绝时明确告知方案设计无法继续，但需求澄清照常进行。
不得用 Skill 方法论或内部源码填充平台事实来输出完整方案。

前置条件：Step 0 探查完成（环境状态 + 工程边界 + 未提交改动情况）。

## 需求澄清：问出来，不脑补

方案中每一条需求只能来自三个合法来源：**用户原话**、**探针与工程文件事实**、
**显式标注「建议（待确认）」的假设**。要点：

- 用户没说过的交互形态、按钮位置、数据细节、存储方式，要么问出来，要么标注待确认。
- 无声脑补即规划失败。

### 决策树与分轮提问

把需求建模为**决策树**：每个决策分叉出挂在它下面的后续决策。
当前能问的问题 = 前置决策已落定、现在就能问的问题集合。推进方式：

- 按轮推进：一轮问完当前所有能问的问题再等答案；答案依赖本轮未决问题的，推迟到后续轮。
- 每轮用一次交互式提问调用提 **<=3 个**问题；待问问题更多时同轮连续调用问完，然后统一等答案。
- 用户每轮的答案重塑决策树：已落定的决策解锁下游问题；重新计算当前可问集合，再问下一轮。
- **完成判据**：当前可问集合为空，且每条假设都有归属（用户确认或已标待确认）。此时才允许输出完整方案。
- **输出门槛**：还有未问清的问题时只能输出「骨架方案 + 集中提问」，不得填充虚构细节。
  用户明确说"你定"的决策面才可自定，并在方案中标注委托来源。
- 高影响问题示例：使用场景与操作者、目标宿主（Cockpit/Plan/Message/Project）、交互形态、
  数据流向、是否持久化、新建能力还是改造现有工程、目标目录。

### 事实自己查，决策问用户

- **事实**（扩展点 Point 的存在性、现有契约、SDK 导出、工程结构、环境状态）永远自己查。
  读文件、跑探针、必要时派子代理。禁止把可自查的事实问用户（把用户当搜索引擎）。
- 查询不阻塞访谈：进行中的查询视为未落定的前置，只有它下游的问题等待；其余问题照常问。
- **决策**（场景、宿主、交互形态、数据流向、持久化等用户偏好）必须问、必须等，不代答。

### 不可谈出答案的问题

有些问题谈不出来，只有看到东西才能反应（"列表怎么排""面板交互长什么样"）。识别后停止追问：

- 处理方式二选一：给合理默认值进 1b 并标「dev 期可调」，随方案批量裁决；
  或用户明确想先看效果时，做一次性原型再回来回答。
- 禁止在访谈里对这类问题反复换措辞，那是会话膨胀的主因，也是脑补的温床。

### 提问交互形式（硬性）

- 提问必须走**环境的交互式提问工具**（opencode 的 `question`；其他 harness 用等价物），一次调用批量提问。
- 每条问题给 2-4 个选项、短 label + 一句描述、推荐项放首位并标「（推荐）」、保留自定义回答；
  允许多选的场景开启 multiple。
- 发现信息缺口**当场问**，不攒到方案末尾让用户逐条回复文本。
- 无交互式提问能力的环境：回退为编号文本问题并说明，等用户逐条回复，禁止代用户作答。

### 可追溯性

「1a. 用户已明确的需求」中每一条都必须能追溯到用户原话或用户的明确确认。
追溯不到的移入 1b 或删掉。

## 规划步骤

1. **需求拆解**：用户目标、主要场景、操作对象、数据流向。
2. **拓扑决策**：
   - 新建工程一律用 `capability-fullstack` 建完整能力工程：交付单位是上传包，用户看到完整结构。
   - 前端/后端组合不是换模板的理由，而是**成员组合**：纯前端只留前端成员目录，纯后端只留后端成员，
     全栈两者都留；模板示例成员按方案增删（成员为目录发现制，见 02），删改经确认，validate 复验。
   - 已有能力工程要新增插件，不新建工程，按 02 的加成员路径处理。
   - `frontend-basic` / `backend-basic` 单插件模板不是 Skill 路径：产物无 `packages.json` 结构，
     pack 产物不可上传（见 06），仅作为存量或用户自建工程出现。
3. **扩展点与权限选型**（Step 1B，查开发运行时数据）：用 MCP `search_knowledge` 按需求语义检索
   （如"驾驶舱工具栏""弹窗权限"），以明确发布的扩展点/能力事实为来源。
   检索不到或未精确解析的目标标"待契约复验"，不借内部源码补齐。
   禁止凭名字猜扩展点 ID 或权限；本文件中的 ID 仅为格式示意。
4. **数据契约草案**：前后端共享 payload 字段草案（只定义一次，实现时落到单一权威契约）；
   存储需求（后端建表）；是否需要跨成员通信（以契约 Service 知识为准）。
5. **目录与命名**：目标目录、插件 ID、各成员命名。
   规则以 `fh2-plugin create --help` 与契约 tooling 机器事实为准（前缀 `official_`/`exp_` 仅为示意）。
6. **验证与交付计划**：generate/types → validate → 单测 → typecheck → build →（可选 dev/preview）→ pack。

## 《插件设计方案概要》输出模板

固定使用以下结构输出，等用户确认后进入 Step 2。**方案记录决策与契约，不内联实现代码**；
文件路径只允许出现在目标目录、成员 ID 这类结构性决策里（易过时的实现细节留给编码阶段）：

```markdown
# 插件设计方案概要
## 1. 目标与场景
### 1a. 用户已明确的需求（每条可追溯到原话或确认）
### 1b. 建议假设（逐条待确认：采纳 / 修改 / 删除）
## 2. 拓扑与模板（推荐 + 理由）
## 3. 插件清单（ID、名称、前端/后端侧、目标目录）
## 4. 前端设计（扩展点、插件界面、state、所需权限）
## 5. 后端设计（Handler/事件/工作流、schema.sql、所需权限）
## 6. 数据契约草案（payload 一次定义；未定稿处标注"待契约复验"）
## 7. 环境状态（探针摘要 + 将执行的补齐动作，需确认）
## 8. 验证、测试与交付计划
## 9. 范围外（Out of Scope）
## 10. 遗留问题与委托项（低影响、可委托代定）
```

方案中的平台事实（扩展点、权限、API 细节）逐条标注来源层级。
查证不到声明的事实标「需验证」并停止该细节设计，不静默输出：

| 来源标注 | 含义 |
| --- | --- |
| `[来源: 生成类型]` | 工程生成类型/工程锁定 SDK 中的声明（编码期最终事实） |
| `[来源: 契约事实]` | 开发运行时数据 factResourceUris 明确发布的机器事实 |
| `[来源: 知识条目]` | 开发运行时数据公开知识正文（与事实冲突时报告） |
| `[来源: 用户原话]` | 用户在提问轮明确给出的决策 |
| `[需验证]` | 所选数据查不到声明；该细节停止设计，留待补源或契约决策 |

环境未就绪时只能输出不含平台细节的骨架和问题。第 7 节列出用户确认过的下载入口/tag/目录、
安装/构建/link 待确认动作与影响。

1b 裁决也走交互式提问：方案输出后用一次批量调用逐条确认（采纳 / 修改 / 删除），
全部裁决且用户确认方案后才进入 Step 2。1b 为空时直接请求整体确认。

第 8 节需覆盖三项：**测试标准**（只测外部行为与契约，不测实现细节）、
**测试范围**（哪些成员/契约要补聚焦单测）、**先例**（沿用模板自带 `tests/` 的既有写法）。
随后才是验证序列（generate/types → validate → 单测 → typecheck → build → 可选 dev/preview → pack）与交付物。

第 9 节明确写出排除项（如"不做国际化""不迁移旧 v1 demo"式的裁决），防止范围蔓延；
拿不准是否排除的内容当场提问裁决。第 10 节只放**低影响、用户可委托代定**的遗留项；
高影响问题必须在提问轮解决，不得遗留到这里。

## 领域词汇表

本表是本 Skill 全部文档的权威用词，也是唯一术语权威（维护侧规则不进公开树，所以放在这里）。
四层业务交付自上而下嵌套，工具和知识来源另列。第四列写明哪些说法不能互相代替：

| 术语 | 定义 | 代码标识 | 容易混用的说法 |
| --- | --- | --- | --- |
| 插件 | 可独立构建与上传的最小单元：前端插件贡献界面与扩展，后端插件提供接口、事件与流程 | `fh2-plugin.json`、`activate` | 能力、能力工程、整个上传包 |
| 能力工程 | `capability-fullstack` 生成的工程根，含一个或多个能力，前后端成员与本地模拟数据共享一套配置 | `capability-fullstack`、`packages.json` | 单插件工程、整个工具箱、工程容器 |
| 上传包 | `pack` 产出的 zip 制品：根 `packages.json` + 各插件目录的 `plugin.json` 与 `dist/` | `fh2-plugin pack`、`packages.json` | 分发压缩包、安装包、单个插件 zip |
| 前端源清单 | 前端插件的声明文件：ID、入口、权限、要挂的扩展点 | `fh2-plugin.json` | 后端源清单（同名但字段不同）、构建产物清单 |
| 扩展点 | 宿主预留的界面位置（工具栏按钮、左面板等），插件只能往这些位置放东西 | `extensions[].point` | 插槽、slot、路由 |
| 扩展 | 插件对某个扩展点的具体贡献，即「在这个位置放什么」 | `ctx.extensions.contribute()` | 扩展点本身 |
| 能力 | 宿主提供给插件的功能：前端按 `permissions` 声明后判空获取，后端按 `allowlist` 申报后全局注入 | `ctx.capabilities.get()`、`allowlist` | 能力工程、插件 |
| 插件界面 | 插件自己的界面代码，挂在宿主给的容器里，拿不到 `ctx` | `defineView` | 页面组件、宿主页面、扩展点 |
| 后端接口处理函数 | 后端插件对外暴露的一个接口，由文件路径与导出名派生接口名，统一从 `/plugin/invoke` 调用 | `handlers/`、`h_<domain>_<action>` | HTTP 路由、controller、接口地址 |
| 流程 | `workflows/*.json` 声明的依赖图，由触发轴启动、按 `needs` 执行步骤，可等待与重放 | `flows[]`、`run_script`、`needs` | 脚本、handler、定时任务 |
| 触发轴 | 流程的启动方式：外部调用、定时、事件消息、业务通知、代码启动，一份流程可声明多条 | `trigger.api/schedule/stream/bizNotify/job` | 事件、信号、轮询 |
| 信号 | 投递给流程挂起步骤的一次外部输入，用于人工确认或选择 | `wait_signal`、`await.signal`、`/signals/` | 事件、回调、WebSocket 消息 |
| 幂等键 | 让"重复执行结果相同"的业务稳定键，写操作必带、读操作不带 | `Idempotency-Key`、`ctx.idempotencyKey`、`ctx.stableId()`、`bizId` | 随机 ID、防重表、数据库主键 |
| 本地调试页面 | `dev` 启动的本地模拟宿主页面，带多宿主容器与热更新，只是模拟 | `fh2-plugin dev` | 调试工作台（旧称）、真实宿主 |
| 司空 | 插件最终部署运行的产品环境；`preview` 连接的真实系统就是它 | `preview` | 把 FH2 或 FlightHub 2 当产品主称 |
| 授权源码 | 从用户确认的入口取得固定 tag/commit 的官方发行源码，先 frozen 安装依赖再构建 | 插件化开发者工具、`--platform-root` | FH2 npm 安装通道、内部维护仓 |
| 开发运行时数据 | Toolchain 自带 `developer-runtime/`：manifest、知识/事实映射、后端注入面、Schema；非完整 Contract | `developer-runtime/`、`manifest.sourceVersions.contract` | 完整契约、后端知识 |
| 后端知识 | `knowledge import/use/status` 对应的独立知识内容、身份和项目锁，用于 IDE/DAG | `knowledge import/use/status` | 开发运行时数据、MCP 来源 |
| 探针 | 本 Skill 自带的只读检查脚本：探测 Node、Toolchain 与运行时数据 manifest 的位置和版本，不验证完整数据 | `scripts/resolve-env.cjs`、`execution.status`、`contract.path` | 完整环境验证、交付检查器 |
| registry 诊断 | 只读查看已有第三方/scope 配置，URL 已脱敏，不联网、不选择 FH2 安装来源 | `.npmrc`、`kind=public/custom/null` | 内外网通道推荐 |

## 事实查证（Step 1B，不预存快照）

平台事实不写死在本文件。MCP 优先，先确认服务与工程所选 Toolchain 是同一副本；
不能从已配置的全局 MCP 推断其版本与本地一致。无 MCP 时读取探针 `contract.path` 指向的同包运行时数据：

1. `manifest.json` 的 `sourceVersions` 表示来源版本/状态/摘要，`publishedEntries` 与 `projectionDigest`
   表示这份数据自身的计数与摘要；来源 approvedEntries 不当公开条目数。
2. `knowledge.json.entries` 按 targetId/domain/kind 查正文、evidence 与 uncertainties，不复制另一套知识快照。
3. `resources.json.files['index.json']` 是逻辑索引，其 `documents` 路由指向 `files` 的明确发布别名；
   知识索引同样从映射读取。不存在磁盘 `developer-runtime/index.json`，
   逻辑 document/evidence 不要求同名源文件存在。
4. evidence 只精确查 `resources.json.facts[ref]`，合法文件别名只查 `resources.json.files[alias]`。
   `resolved=false` 保留 `value=null` 和 warning，未知别名/ref 不读任意磁盘文件、不返回整个源文件兜底。
5. 后端注入面与 Schema 分别从同包 `backend.json` 和 `schemas/` 查；
   完整文件/摘要/引用/Schema 校验交给当前 Toolchain 执行。
   所需公开视图缺失、冲突或无法解析时停止相关细节设计并报告。

| 事实类别 | 查证方式 |
| --- | --- |
| 扩展点是否存在、state/static 契约 | `search_knowledge`（kind=point 或按语义检索）→ 读知识 URI → 读 factResourceUris 机器事实 |
| 能力/权限申请 | 枚举用 `list_knowledge`（kind=capability）；具体权限语义用 `search_knowledge` |
| 后端 Handler/触发器/工作流/入口 | `search_knowledge`（domain=backend，按动作语义检索） |
| CLI 参数、用法与退出语义 | 枚举用 `list_knowledge`（tooling/command）；参数核对本次帮助和生产数据，用法/退出语义用 `search_knowledge` 的已审核人工说明，不当机器执行策略 |
| 错误码含义 | `search_knowledge`（按错误码/报错文案检索诊断） |
| 工程结构、目录规则 | 契约 tooling 机器事实 + 生成工程实际结构 |

查证结果的来源 versions 和数据 metadata 分开记入方案第 7 节
（MCP 响应外层结构中的数据摘要通常位于 `data.versions.projection`）；
所选 Toolchain 制品版本与来源契约版本不能混用。
`uncertainties`、warning、阻断状态和未解析事实随结论原样暴露。

## 端到端示例

用户："创建一个道路巡检插件，前端显示巡检记录，后端保存记录。"

正确做法：

1. 先按决策树分轮交互式提问：使用场景（谁在什么时候记）、目标宿主、数据流向与是否持久化。
   交互细节（列表排序、面板形态）属不可谈出答案的问题，给默认值进 1b 标「dev 期可调」，不追问不脑补。
2. 提出合法 ID 集（如 `exp_road_inspection`）与目标目录。
3. 推荐模板 `capability-fullstack`，输出《插件设计方案概要》（用户说过的进 1a，我建议的进 1b 待确认）。
4. 1b 逐条裁决 + 方案/安装确认后进入 Step 2，使用已初始化的授权源码 bin，传 `--platform-root`。
5. 定义记录 payload 一次，实现一条端到端功能 + 聚焦单测，再 generate/validate/typecheck/build。
6. 汇报并询问是否启动 `dev`。

源码初始化先按 00 的 frozen install、构建流程完成，不以 FH2 npm 包替代。
创建命令与参数核对见 02，本文件不重复示例。

## 出口条件

- [ ] 决策树当前可问集合为空；1a 每条能指到用户原话或用户的明确确认。
- [ ] 1b 每条假设都有裁决记录（采纳 / 修改 / 删除）。
- [ ] 进入 1B 时 `execution.status === 'ready'` 且 `contract.path` 非空，且已实际读取所需运行时数据；
      拒绝补齐时未输出带平台细节的方案。
- [ ] 《插件设计方案概要》已按 10 节结构输出且用户确认（或用户明确委托按推荐项执行）。
- [ ] 方案中每个扩展点/能力/API 名称都能指出查证来源（`[来源: 生成类型]` 或 `factResourceUris`）。
- [ ] 方案第 7 节记录了来源 versions 与数据 metadata，未混淆 Toolchain 制品版本与来源契约版本。
- [ ] 方案第 2/3 节写明了拓扑、插件 ID、目标目录与权限草案，且没有未决项（未决项已标待确认并进 1b）。

## 反模式

- 不问或只问一轮，就输出填充了虚构细节（交互、排序、存储等用户没说过的内容）的完整方案。
- 还有可问的问题就写完整方案。
- 把高影响问题贴成方案末尾的文本清单，而不是交互式提问。
- 把可自查的事实（扩展点存在性、现有契约、工程结构）问用户，把用户当搜索引擎。
- 对不可谈出答案的问题（交互细节、排序）反复换措辞追问，而不是给默认值进 1b。
- 跳过方案直接 create。
- 方案里写猜测的扩展点 ID、权限、`ctx` 方法。
- 问卷式单轮轰炸超过 3 个问题。
- 环境缺失时把方案和安装混成两次打断。
